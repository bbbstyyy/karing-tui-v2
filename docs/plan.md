## 1. 目标与不可退化约束

### 1.1 产品定位

实现一个能够长期运行的 Linux 代理管理工具：使用终端界面管理 Karing 风格的订阅、节点、测速组、分流组、DNS、规则集及连接状态，复用经过验证的 KaringX/sing-box 网络内核。

它不是 Flutter 页面逐项翻译，也不是只能切换节点的 Clash API 看板。业务模型、配置编译和持久化必须由独立于 TUI 的服务承担。

### 1.2 硬性需求

| 编号 | 要求 | 不允许的退化 |
| --- | --- | --- |
| R01 | Linux-only，普通用户可运行 | 核心功能依赖 root、sudo、CAP_NET_ADMIN 或桌面会话 |
| R02 | 不实现 TUN 或透明代理 | 通过导入配置偷偷启用 TUN、TPROXY、redirect、路由或防火墙修改 |
| R03 | 保留 CN 预设及默认开关 | 用自制两条规则替换原预设，或者默认打开全部服务/广告规则 |
| R04 | 保留多来源、多层、可排序分流 | 丢失自定义、GeoSite、GeoIP、ACL、FINAL 的来源与优先级，或重新引入订阅/ISP 分流层 |
| R05 | 保留多种出站目标与自定义测速组 | 所有分流组只能绑定一个全局 Proxy |
| R06 | 保留分流组 DNS 绑定 | 只提供两个全局 DNS 地址，或者保存了绑定但运行时不生效 |
| R07 | 尽可能保留适用于 Linux 的原功能 | 丢失订阅节点的协议参数、必要来源元数据、过滤/流量/更新能力；但订阅提供的分流规则不进入运行时分流 |
| R08 | 以长期稳定为基础 | 关闭 TUI 就中断代理、无限重试、资源无上限、无法恢复配置 |
| R09 | CN 环境可离线启动已有配置 | 每次启动强制访问 GitHub、下载规则或刷新订阅 |
| R10 | 明确、可验证的故障行为 | 找不到节点、DNS 或规则时静默改为直连 |
| R11 | 所有持久变更可追踪、可恢复 | 直接覆盖正在使用的唯一配置文件或规则文件 |
| R12 | 来源、许可与兼容性可审计 | 宣称未经测试的百分之百兼容，或不记录内核及规则来源 |

### 1.3 优先级

正确分流与安全边界 > 数据完整性和可恢复性 > 长期可用性 > 功能覆盖 > 操作便利 > 界面装饰。

“稳定”不是不显示错误，而是错误可识别、影响有边界、有效状态不会被破坏，并且不通过隐式旁路掩盖失败。

### 1.4 明确排除

不实现 TUN、TPROXY、iptables/nftables 配置、系统路由接管、系统 DNS 劫持、内核模块安装、自动提权。默认不修改 GNOME/KDE 系统代理或 Shell 启动文件。

Android/iOS/tvOS、Windows/macOS 平台集成、移动端 Per-App VPN、iCloud、系统托盘和 Flutter 窗口不在目标范围。FakeIP 不属于当前代理感知型入口的目标能力，不为其保留隐式启用路径。

普通 HTTP/SOCKS 代理只能处理应用实际送入代理的流量，不能保证整机所有流量或所有 DNS 查询经过本程序。HTTP、SOCKS 的能力及 UDP 支持必须分别验证，不承诺替代 VPN。[S19][S26]

## 2. 源码核查结论与证据边界

### 2.1 审查对象

以固定提交的公开代码为依据，交叉核查业务入口、订阅及状态管理、设置模型、分流与测速页面、CN 预设、依赖与资源声明、许可证，以及相关内核控制代码和官方说明。公开源码观察、产品要求和本项目设计在本文中分开表述。

本次未编译或运行 Karing/内核，未完成规则二进制的行为验证，也未开展长期压力测试。下文的稳定性指标和兼容测试均为开发验收要求。

### 2.2 关键发现

| 证据 | 已确认的内容 | 对本项目的约束 |
| --- | --- | --- |
| `README_cn.md` | Flutter 前端、修改版 sing-box，多订阅、分组及备份同步能力 | 兼容对象是业务行为，不仅是 UI [S01] |
| `lib/app` Git tree、`pubspec.yaml`、业务文件 import | 当前公开快照中缺少被引用的 `utils`、`local_services` 等目录，另有 `../vpn-service/` 本地依赖 | 不以“直接删除 Flutter 后即可构建”为前提；缺失逻辑必须通过规范与夹具补齐 [S02][S03][S04] |
| `ServerManager.diversionGroupSorted()` | 上游存在自定义 → 订阅 → GeoSite → GeoIP → ACL → FINAL 的逻辑排序 | 本项目按需求明确去除订阅/ISP 层，只实现自定义 → GeoSite → GeoIP → ACL → FINAL [S04] |
| `DiversionGroupSetting`、`getDiversionGroups()` | 规则组、出站绑定、DNS 列表分别保存并组合 | 不把匹配规则与某个具体节点永久写死 [S04] |
| `diversion_rules_screen.dart` | 全局/来源开关、每组目标、地区规则追加、组 DNS 编辑、NONE 与 FINAL 的区别 | UI 和编译器都必须保留这些语义 [S06] |
| `urltest_group_custom_screen.dart` | 跨启用订阅选取节点，显式 tags 和动态 regexs | 自定义测速组必须是一等实体 [S07] |
| `ServerManager.loadFrom()` | 上游具备保留/启用订阅分流规则的能力 | 本项目明确不继承该能力：只导入节点及必要元数据，订阅 route/rules/rule-provider/ISP 分流不进入运行时路由树 [S04] |
| `SettingConfigItemDNS` | resolver、outbound、direct、proxy 多类 DNS 配置 | 必须建模启动解析、节点解析和目标解析的不同用途 [S05] |
| `SettingConfigItemRuleSets` | GeoSite/GeoIP/ACL、自动追加地区规则、禁用 ISP 规则等独立开关 | CN 预设不是地区直连功能的全部 [S05] |
| 内核 `experimental/clashapi/configs.go` | 所查候选的 `PUT /configs` 仅返回 NoContent，未实现完整配置重载；PATCH 只处理模式 | 不得把 HTTP 204 当作配置已应用 [S14] |
| 内核 `Makefile`、`go.mod` | 候选使用 `github.com/sagernet/sing-box` 模块名；Makefile 中存在 `@latest` 工具调用 | 从明确的 KaringX 源码构建，工具链也必须锁定 [S11][S12] |

### 2.3 必须纠正的简化假设

1. **有序数组不是问题，丢失上层结构才是问题。** 最终可以生成 sing-box 的有序 `route.rules`；但持久模型必须保留层、组、绑定与来源映射，能够重新编译和解释。
2. **CurrentSelected 不等于某个永久固定的手选节点。** 它是当前选择的引用，可以指向受支持的自动组；具体允许的候选类型需通过兼容夹具确认。
3. **规则来源层与规则集类型不是同一维度。** CN 预设中的自定义组即使引用 `geoip:*`，也不能被自动移入第四层。
4. **“保存了 DNS 绑定”不等于“目标连接使用了该 DNS”。** 代理协议可能转交域名给远端解析，必须验证实际解析路径。
5. **支持 Clash API 不意味着实现所有 Clash API 行为。** 每项接口必须有能力检测与行为测试，尤其不能假定支持热重载。
6. **沿用 GPL 代码或资源与使用原项目名称是不同问题。** 分离进程也不能作为忽略许可义务的理由。[S10]

### 2.4 尚不能仅凭公开源码确定的行为

缺失的 `singbox_config_builder.dart`、`proxy_conf_utils.dart`、`auto_conf_utils.dart`、`clash_api.dart` 和相关服务封装，意味着以下内容需要在 M0/M2 建立行为夹具：

- 私有地址直连、模式规则、DNS/嗅探预处理在最终运行配置中的确切插入位置。
- 地区 GeoSite/GeoIP 自动追加规则与用户内建条目的最终编译关系。
- Karing 自定义字段组合的 AND/OR、否定和平台条件转换规则。
- 订阅中复杂节点来源（如 proxy-provider）如何安全物化为节点，同时确保其 MATCH/FINAL、rules、rule-provider 和 ISP 分流不进入运行时路由树。
- 每组 DNS 在不同出站协议、域名/IP 请求下的实际生效路径。
- 应用发行包与内核源码、构建标签、规则包之间的精确映射。

无法确定的行为必须标为“待验证”，不能用推测填成“已兼容”。有明确、安全且必要的行为差异时，应通过 ADR 和兼容性说明记录，而不是复制疑似缺陷。

## 3. 功能范围与优先级

P0 是首个正式兼容版本的发布门槛；P1 是同一产品路线中的后续能力，不代表永久删除。内部原型可以只实现部分功能，但必须标识为原型。

| 能力 | 优先级 | 实现要求 |
| --- | --- | --- |
| Linux 普通用户运行、服务与 TUI 分离 | P0 | 无桌面、无 root 可启动；TUI 生命周期不影响服务 |
| 内核启动/停止/状态/恢复 | P0 | 进程所有权明确、有限退避、配置与内核匹配 |
| Rule / Direct / Selected 三入口 | P0 | Loopback Mixed，端口可配，语义明确 |
| 五层分流、来源开关、排序、FINAL | P0 | 自定义 → GeoSite → GeoIP → ACL → FINAL；订阅/ISP 不构成分流层 |
| CN 全部 28 个预设组及相关资源 | P0 | 保留顺序、默认状态、绑定可编辑，离线可用 |
| CurrentSelected、全局及自定义 URLTest、固定节点 | P0 | 跨订阅引用、稳定 ID、错误目标不旁路 |
| DNS 分层、每组绑定、静态解析配置 | P0 | 依赖无环、作用范围可解释、实际流量验证 |
| 原生 sing-box 配置与常见分享链接 | P0 | 保留相关节点选项及合法规则；禁止不受支持的特权入口 |
| Clash/Clash.Meta、V2Ray/Base64、Sub/GitHub 订阅 | P0 | 按节点字段维护兼容矩阵；订阅分流内容按设计忽略并在导入报告中明确列出 |
| 多订阅、启停、过滤、重命名、排序、流量信息 | P0 | 订阅更新不破坏分流绑定、收藏与选择 |
| 定时更新、有限测速、故障隔离 | P0 | 无重入、无无限队列、失败继续使用有效快照 |
| 连接、流量、日志、分流解释、诊断 | P0 | 观测通道失效不重启健康内核；标明数据是否过期 |
| 自有版本化备份与恢复 | P0 | 一致快照、恢复预检查、失败不覆盖有效状态 |
| Karing 备份导入 | P1 | 只读迁移、格式校验、逐项报告，不直接接管原目录 |
| 前置代理/代理链、完整高级 TLS/Mux 选项 | P1 | 用户态支持且内核能力已验证时保留；独立依赖图与无环校验 |
| WebDAV、LAN 同步、自动备份策略 | P1 | 显式启用、认证、冲突检测、事务应用 |
| 历史统计、规则编辑辅助、二维码文件导入/导出 | P1 | 限额与隐私控制，不依赖摄像头 |
| 用户态 WARP 等附加能力 | P1 调研 | 不因追求数量引入特权或未经验证的账号/协议流程 |
| 内核及规则更新检查 | P0 基础/P1 自动化 | 人工确认发布升级；规则更新有独立回滚 |
| 平台 VPN、透明代理、系统设置接管 | 排除 | 不设置隐藏开关恢复这些能力 |
| 商业推广、内嵌服务商商城、默认遥测 | 排除 | 不属于代理核心功能，不成为运行依赖 |

## 4. 总体架构

```text
                         管理面
       TUI / CLI / 自动化脚本
                  |
          本地受保护 Unix Socket
                  |
       +----------v-----------------------------------+
       | 常驻 daemon：唯一配置写入者                   |
       | 领域服务 / 调度器 / SQLite / 编译器 / 监督器   |
       | DNS 策略 / RuleSet 管理 / 观测聚合 / 备份      |
       +----------+------------------+----------------+
                  |                  |
          生命周期、配置文件   经验证的 Clash API
                  |                  |
       +----------v------------------v----------------+
       | 独立 KaringX/sing-box core                    |
       +----------^-----------------------------------+
                  |
        127.0.0.1 的 HTTP/SOCKS Mixed 入口
                  |
               应用流量
                         数据面
```

### 4.1 组件职责

- **TUI/CLI**：展示快照、提交命令、显示变更预览；不直接写数据库、生成内核配置或拥有内核进程。
- **Daemon**：持有领域状态、协调任务、验证和应用变更、维护恢复记录，向多个前端提供版本化本地接口。
- **Compiler**：纯输入模型到确定性输出，保留来源映射，不执行网络请求或 UI 操作。
- **Core adapter/supervisor**：处理特定内核版本的能力、协议与生命周期；不把供应商差异散落到各页面。
- **Core**：承担代理协议、连接转发、路由匹配和经验证的 URLTest；应用数据不经过 Go 管理服务转发。

初期可以使用同一个 Go 可执行文件的 `tui`、`daemon run` 等子命令，配一个独立内核文件。不要为了“单二进制”提前把内核嵌入 TUI 进程。

### 4.2 状态所有权

Daemon 是唯一权威写入者。设置、订阅、分组与绑定是声明状态；当前进程、连接、测速结果是观测状态；两者不能混为一谈。

多个 TUI 可连接同一服务，写入必须带配置 revision 并进行乐观并发检查。前端断开不取消已经被服务正式接收的配置事务；可取消任务需要显式任务取消协议。

### 4.3 入口设计

| 入口 | 本项目建议默认 | 行为 |
| --- | --- | --- |
| Rule | `127.0.0.1:2080` | 正常使用入口，执行模式及完整多层分流 |
| Direct | `127.0.0.1:2081` | 显式绕过业务分流，走 DIRECT，主要用于诊断和明确的直连操作 |
| Selected | `127.0.0.1:2082` | 显式绕过业务分流，交给 CurrentSelected；界面可解释为选定出口入口 |
| Core 控制端口 | Loopback，可配置 | 仅供管理服务使用，必须认证，不向 LAN 开放 |

上述 2080/2081/2082 是本项目建议，不是 Karing 原默认值。所查 Karing 设置分别为规则 3067、直连 3065、转发 3066、控制 3057。[S05]

Direct 与 Selected 入口是明确的旁路工具，不能让用户误以为其仍受 Rule 入口的广告/阻断规则保护。Selected 表示“按当前目标转发”，不是对出口国家或链路隐私的保证。

端口冲突必须报错，不得静默换端口导致应用继续连接旧服务。启用 IPv6 Loopback 或 LAN 共享属于独立配置变更；默认只开放本机。LAN 共享只能在 P1 显式认证和风险提示后实现。

## 5. 进程生命周期与长期运行

### 5.1 生产运行方式

推荐 daemon 前台运行，由 `systemd --user` 管理；TUI 只是可随时连接、退出的客户端。程序本身不进行 double-fork，也不在后台不断创建无法追踪的内核。[S21]

用户服务应评估并测试：`Restart=on-failure`、启动频率限制、`KillMode=control-group`、`UMask=0077`、合理停止超时、日志与资源限制。内核由 daemon 监督，daemon 由 systemd 监督，避免两个互相竞争的内核重启器。

关闭 TUI、终端缩放、SSH 断线不得停止仍由用户服务托管的代理。**但退出登录后继续运行、开机启动取决于用户管理器与 lingering 配置；启用 lingering 的授权取决于系统策略，不能承诺所有 Linux 都完全不需要管理员协助配置用户服务。** 这不改变代理核心无需特权的要求。[S22]

非 systemd 环境支持显式 `daemon run`，交给已有监督器管理；文档必须说明其会话生命周期，而不能把普通前台进程说成永久后台服务。

### 5.2 生命周期状态机

```text
Stopped -> Starting -> Running
              |          |
              v          +-> Applying -> Running
           StartFailed                \-> RollingBack -> Running / Failed

Running -> CoreExited -> Backoff -> Starting
                         |
                         +-> CircuitOpen（服务仍可诊断，停止重启风暴）

Running -> Stopping -> Stopped
```

网络不可达、节点失效和观测接口中断是独立健康维度，不应全部转换成 CoreExited。手动停止要记录为停止意图，不能被健康检查重新启动。

### 5.3 必须落实的进程规则

- 使用锁保证同一配置目录仅有一个 daemon；校验锁目录和 socket 的所有权。
- 只操作自己创建或经严格身份校验的子进程；PID 文件不是充分身份依据，要考虑 PID 复用。
- 不使用 `pkill sing-box` 等全局进程名终止方式。
- 启动、停止、检查均有 deadline；先正常终止，超时才强制终止，并始终回收子进程。
- 持续消费 stdout/stderr，避免管道写满使 core 卡死；日志消费者也必须有界。
- systemd 模式靠 cgroup 清理遗留子进程；无 systemd 模式必须实现并测试明确的父子退出策略。
- daemon 崩溃后允许通过监督器恢复，但不承诺既有连接毫无中断；**保证 TUI 崩溃不影响 core，不等于保证 daemon/core 崩溃无损。**
- 连续确定性启动失败使用有限指数退避和熔断；建议初值 1/2/4/8 秒、上限 60 秒，10 分钟内连续失败 5 次后进入需要诊断的状态。这些是初始设计参数，需测试确认。
- 临时外网故障只降低网络健康状态，不反复重启 core；恢复后先检查当前连接能力，再渐进恢复任务。

### 5.4 启动不依赖互联网

顺序应为：验证本地状态和资源 → 找到最近有效代际 → 检查对应内核 → 启动并验证本地入口 → 恢复观测 → 错峰安排非关键更新。

无网络时仍应启动已有有效配置的本地服务；这不等于外部代理节点一定可达。首次没有节点时保持可配置、可诊断状态，不自动填入 DIRECT 假装代理可用。

## 6. 完整多层分流规范

### 6.1 两个维度同时保留

**规则匹配维度：** 来源层 → 来源内的分流组 → 组内有序匹配规则。

**出口选择维度：** 命中的分流组 → 目标策略 → 选择器/测速组 → 实际节点或 DIRECT/BLOCK。

```text
Rule 入站
   |
   +-- 模式、可选私有地址策略、经验证的非终结预处理
   |
   +-- L1 自定义分流组（包括由 CN preset 初始化的组）
   +-- L2 GeoSite 分流
   +-- L3 GeoIP 分流
   +-- L4 ACL 分流
   +-- L5 FINAL
                 |
                 +-- DIRECT
                 +-- BLOCK
                 +-- CurrentSelected -> 节点或支持的自动组
                 +-- Global URLTest -> 实际节点
                 +-- Custom URLTest -> 跨订阅候选 -> 实际节点
                 +-- Specific Node（ProfileID + NodeID）
```

上游 `diversionGroupSorted()` 可确认原实现曾包含订阅/ISP 层；本项目按需求将其从领域模型与运行时编译中移除，形成五层逻辑排序。图中的预处理、私有地址和模式插入位置仍需依据最终运行配置夹具完成确认，不能仅用页面排列猜测。[S04][S06]

### 6.2 排序规范

| 层 | 持久化顺序 |
| --- | --- |
| L1 自定义 | 用户组顺序、组内规则顺序；CN 初始顺序来自原预设 |
| L2 GeoSite | 用户选用的 GeoSite 条目顺序；地区追加策略独立建模 |
| L3 GeoIP | 用户选用的 GeoIP 条目顺序；地区追加策略独立建模 |
| L4 ACL | 用户选用的 ACL 条目顺序 |
| L5 FINAL | 唯一有效最终目标，不参与随意拖动 |

不能按名称、国家、延迟或者规则集前缀重新排序。数据库查询必须显式排序，不能依赖 Map 遍历顺序。迁移时出现相同序号，应稳定处理并产生可追踪的规范化结果。

普通终结路由按有效顺序命中；`sniff`、`resolve` 等非终结动作不等于立刻选定最终出口。编译器必须区分动作类别。[S18]

### 6.3 开关不是一个 Enabled 就够

必须独立保留：

| 范围 | 状态 |
| --- | --- |
| 订阅 | 是否启用、更新策略、节点过滤与节点可用性；不提供订阅分流规则开关 |
| 全局来源 | 禁用自定义分流组 |
| 内建层 | GeoSite、GeoIP、ACL 各自启用状态 |
| 地区 | 自动追加地区 GeoSite、自动追加地区 GeoIP |
| 单个分流组 | 启用、停用/NONE、目标绑定、独立 DNS 绑定 |
| 运行模式 | Rule、Global、Direct 等经验证的模式语义 |
| 私有地址 | `privateDirect` 等独立策略开关 |

基线代码中存在 ISP 分流相关开关，但本项目不建模也不编译订阅/ISP 分流。自定义分流禁用、GeoSite/GeoIP/ACL 开关和地区 GeoSite/GeoIP 自动追加仍独立保留；导入订阅携带的分流内容只进入诊断报告，不会进入任何分流层。[S05]

`NONE` 表示该组不参与生效分流，不是 DIRECT，也不是 BLOCK。FINAL 不得为 NONE。关闭一个组以后，流量可以继续落到后续组；目标丢失造成的错误不能被解释成“用户关闭了这个组”。[S06]

### 6.4 CN preset 所在层

例如“国内直连”组同时引用 `acl:ChinaIp` 和 `acl:ChinaDomain`，仍然是 L1 中的一个自定义组。它不能被拆开后分别移动到 GeoIP/GeoSite/ACL 层。

GeoSite/GeoIP/ACL 既可以是低层独立分流条目，也可以是高层自定义组（包括 CN preset）的匹配材料。这两种用途必须同时支持；订阅来源不得创建高层分流组。

### 6.5 匹配语义与平台裁剪

建立显式布尔表达式模型，支持需要兼容的 domain、suffix、keyword、regex、IP CIDR、rule-set、端口、网络类型、进程等条件及逻辑组合。**不能把所有字段统一 OR，也不能统一 AND。** sing-box 默认规则对不同字段组有明确组合方式，Karing 自定义格式还存在额外转换，需要逐项确认。[S17]

Linux 无 TUN 场景的进程识别是可选增强，不是必需匹配依据。转发流量、权限限制或信息缺失时应显示 Unknown；不能提权来补齐。

对 Android package、Windows/macOS 特有 process 条件：保留原始字段供迁移报告使用，依据已经确认的表达式语义，将不可满足分支显式处理为 false，或拒绝启用该规则。只有证明 domain/IP 分支独立有效时才能保留该分支。

**绝不能直接删除所有不支持字段，留下一个无条件匹配的规则。** 空匹配组应报错或显式停用。例如 Google Play 的域名分支可以在 Linux 有意义，但不能因为删除 package 字段改变它与其他字段的组合含义。

### 6.6 目标解析与失败策略

目标使用类型化引用，而不是任意显示名称。固定节点用 `(ProfileID, NodeID)`，自动组用稳定 GroupID，CurrentSelected 保持符号引用。

所有代理目标失效时，不隐式退回 DIRECT、不跳过安全阻断规则、不静默换成别的国家或订阅。允许用户明确配置组内后备候选，但后备范围必须可见、受约束并参与测试。

存在有效运行配置时，涉及缺失目标、空自动组、无效 FINAL 的新配置不得替换它；首次配置遇到这些问题则保持未就绪状态并报告原因。

### 6.7 订阅分流剥离边界

本项目**不保留来自订阅或 ISP 的分流规则**。无论订阅格式是 Clash、Clash.Meta、sing-box 还是其他可解析格式，导入后都不得生成独立的“订阅/ISP 分流层”。

订阅导入允许保留和使用的内容主要是：节点定义及其受支持的协议/传输参数、订阅来源和更新时间、流量/过期等必要元数据、节点过滤所需信息，以及为了物化节点而必须读取的 provider 内容。若 `proxy-provider` 是获得节点的必要来源，可以在同样的安全、大小、超时和来源约束下解析为节点；它本身不会成为运行时分流规则来源。

以下内容按产品设计从运行时路由模型中剥离：Clash `rules`、`rule-providers` 的路由绑定、sing-box `route.rules`、订阅内 MATCH/FINAL、ISP diversion groups，以及订阅定义的其他路由优先级。源定义的 selector/url-test 也不自动成为本项目的分流目标；用户使用本项目自己的 CurrentSelected、Global URLTest、Custom URLTest 和固定节点模型。

被剥离的分流内容必须在导入/更新报告中明确标记为“按产品策略忽略”，以便审计，但这不算导入失败。订阅更新可以通过节点增删影响引用这些节点的选择组可用性，却不能新增、删除、重排或覆盖五层路由树中的任何 RuleGroup、FINAL 或组 DNS 绑定。

实现和测试必须保证：即使订阅包含无条件 MATCH、FINAL、复杂 rule-provider 或 ISP 分流，也不会遮蔽本项目的 GeoSite、GeoIP、ACL 或 FINAL。若某个节点只有通过无法安全解析的 provider 才能获得，则该节点来源导入失败；不能通过保留整份订阅路由配置来绕过这一边界。

用户可以将 Google 指向 JP-Auto、OpenAI 指向 US-Auto、Telegram 指向指定节点，并分别设置 DNS。修改这些绑定不要求改写上游资源文件。

预设升级采用旧基线、新基线、用户覆盖的三方比较。新增组、删除组、改名、规则内容变化和顺序变化均产生预览；冲突待确认，不能自动覆盖用户目标或移除被引用的组。

`autoAppendRegionGeoSite` 与 `autoAppendRegionGeoIp` 是独立于上述 28 组的机制。CN 默认初始化应保留这两个开关及资源，UI 展示自动生成来源，不能仅靠“国内直连”组冒充实现。

自动条目与用户指定同名条目如何去重、实际插入位置及优先关系必须形成兼容夹具；必须允许在诊断中辨别“CN 预设命中”和“地区自动追加命中”。[S05][S06]

### 7.4 离线规则包

发行包包含以下引用闭包：全部 28 个预设组使用的规则集，包括默认关闭组的规则集，以及 CN 地区自动追加所需资源。资源许可先核查，再决定随包分发方式。

清单记录逻辑标签、相对路径、格式、字节数、SHA-256、来源仓库和提交、规则格式版本、适配内核及许可证来源。这里只规定生成方法，不虚构尚未核算的资源总数或哈希。

运行时只加载已启用规则需要的资源；完整离线包与实际加载集分离，减少内存占用。`geosite:*`、`geoip:*`、`acl:*` 是领域标签，不应直接当成已废弃的旧版内核字段写入配置；由适配器映射到经过验证的 `.srs`/rule-set 表达。[S17]

### 7.5 更新策略

更新下载到暂存区，限制大小，校验哈希与格式，执行规则与引用检查，然后作为新资源代际参与配置事务。当前使用的规则文件不可原地覆盖。

下载失败、格式不兼容、资源缺失或远端不可达时继续使用已验证旧版本并标记 stale。哈希校验只能证明与可信清单一致；来源可信度需要通过固定提交、可信发行清单或签名解决，不能把任意下载文件的自算哈希当成来源认证。

更新通道由用户选择 Direct、Selected 或其他明确路径，不自动使用未知镜像，不在启动时强制联网。开启新规则所需资源缺失时应拒绝该变更，不静默跳过规则。

## 8. 领域模型与配置编译

### 8.1 核心实体

| 实体 | 主要内容 |
| --- | --- |
| ProfileSource | 来源 ID、格式、URL/路径、获取策略、UA、更新时间、最近成功快照 |
| Profile | 名称、启用状态、节点、必要来源元数据、过滤与流量信息；不持有运行时订阅分流规则 |
| Node | 稳定 ID、所属 Profile、显示名称、协议与传输选项、来源定位、可用性 |
| SelectionGroup | 手选/全局自动/自定义自动类型、显式成员、动态规则、测试与后备策略 |
| RuleGroup | 稳定 ID、来源层、来源 ID、组顺序、规则表达式、预设来源 |
| RouteBinding | RuleGroupID、启用状态、类型化 TargetRef、可选 DNSBinding |
| DNSProfile | 解析用途、传输、地址、bootstrap、detour、缓存及静态记录策略 |
| RuleSetArtifact | 标签、来源、版本、路径、哈希、格式与兼容性 |
| ConfigRevision | 不可变声明状态、版本、父版本、变更来源、校验结果 |
| RuntimeGeneration | 编译结果、资源清单、内核锁定、映射文件、应用状态 |

源内容保留必要的未知字段供诊断和未来迁移，但不得无校验地穿透到运行配置。

### 8.2 引用与标识

名称、emoji、订阅中的显示 tag 都不是数据库主键。节点和组名称可变，稳定 ID 不变；内核运行 tag 由本项目映射生成，保证全局唯一。

跨订阅同名节点不得碰撞。节点 ID 对账优先使用源内稳定标识与持久映射；名称或凭据变更不能简单当作同一个节点或完全新节点。无法唯一识别时进入显式对账，不擅自重新绑定敏感分流。

### 8.3 编译流程

```text
声明状态 + 精确版本的预设/规则包 + core capabilities
   -> 格式/字段验证
   -> 引用解析与平台能力检查
   -> 规则、出口与 DNS 依赖图验证
   -> 构建分层 Routing IR
   -> 计算生效资源闭包
   -> 生成有序路由、DNS、出站、入站
   -> 输出 source-map / diagnostics / manifest
   -> 使用同一目标内核进行 check
   -> 进入应用事务
```

Compiler 不下载资源、不读取可变的“最新订阅”，不查询当前 UI 选择状态。所有输入都来自明确 revision。

输出应确定：同样输入和适配器版本产生同样规范化输出。对象键可以规范化排序；**规则数组、层顺序、组顺序及具有优先含义的候选列表绝不能为了 diff 好看而排序。**

### 8.4 来源映射

每条生成规则记录 `generation_id / layer / source_id / group_id / source_rule_index / action`。一个高层规则转换成多条低层规则时仍映射回同一源对象。

编译器不能随意合并来自不同层、不同 DNS 绑定或不同开关的相似规则。只允许有证明和测试的等价优化，默认优先可解释性。

### 8.5 空组、循环与非法入口

编译期必须发现：悬空引用、空候选组、CurrentSelected 自引用、selector 循环、代理链循环、DNS bootstrap 循环、重复运行 tag、多个 FINAL、非法端口、缺失规则资源及不支持的内核字段。

生成配置采用明确入口白名单；任何导入路径都不能输出 TUN、TPROXY 或修改系统网络的动作。无有效匹配条件不等于全匹配；全匹配必须是显式、经过来源验证的操作。

## 9. DNS 的分层语义

### 9.1 必须保留的解析角色

| 角色 | 用途 | 关键约束 |
| --- | --- | --- |
| Resolver/Bootstrap | 解析 DNS 服务自身的域名等启动依赖 | 不形成“先有代理才能解析代理所需 DNS”的环 |
| Outbound/Node DNS | 解析代理节点的 server 域名 | 与目标网站解析分开；有可启动的引导路径 |
| Direct DNS | 直连目的地解析 | 适用于明确的直连策略 |
| Proxy DNS | 代理目的地相关解析 | 传输是否经代理必须显式、可验证 |
| Group DNS | 分流组指定的解析覆盖 | 不覆盖节点启动解析，不因 UI 保存成功就声称生效 |
| Global fallback | 未配置覆盖时的全局解析策略 | 与路由 FINAL 是不同概念 |

这些角色以 Karing 的 DNS 模型和官方说明为依据，具体编译由本项目适配器实现。[S05][S16]

原界面对非 BLOCK、非 FINAL 分流组开放独立 DNS 编辑，并限制单次组选择的服务器数量；本项目首先兼容这种已确认能力，不将任意 FINAL DNS 编辑冒充既有行为。[S06]

### 9.2 代理感知型入口的限制

HTTP CONNECT 与 SOCKS5h 可以向代理传递域名，但某些出站会将域名交给远端服务器解析。此时仅设置 `dns.rules` 未必让组 DNS 控制最终目标解析。

实现必须逐协议验证：是由本地内核在指定策略下解析、由选定 DNS 经指定出口解析，还是按协议交给远端解析。若要兑现“组 DNS 覆盖”，必须生成确实生效的解析动作或使用内核相应能力；不能一边把域名原样交给远端，一边在 UI 中声称本地指定 DNS 已被采用。[S16][S18]

### 9.3 路由与 DNS 的相互依赖

域名规则优先级、需要目标 IP 的规则、DNS 规则都应由同一个 IR 派生。不能为了 GeoIP 判断，先把所有目标送到直连 DNS，再决定它们应该走代理。

应明确记录何时拥有域名、何时需要解析、使用哪个 DNS、是否得到 IP、哪些规则仍不可判断。DNS 上下文不足时不得伪造确定的匹配结论。

组 DNS 的服务器选择与其传输 detour 是两个属性。一个组使用 US-Auto 出站，并不自动证明 DNS 查询也经 US-Auto；用户意图和编译结果必须一致，并通过受控 DNS 服务验证。

### 9.4 默认策略与安全差异

CN 初始化可以提供国内可达解析与经代理的解析模板，但所有具体服务器、连接方式和启动路径都要经过目标环境验证。不得宣称某个公共 DNS 永远可达，也不把上游复杂默认列表误写成简单二选一。

本项目不启用 FakeIP，不接管系统 DNS，不监听特权 53 端口。ECS/客户端子网等涉及隐私的选项默认关闭可作为有记录的安全差异；需要兼容迁移时明确提示，不静默改变。

### 9.5 缓存与失败

- 尊重有效 TTL 并设合理上下限；不同策略的缓存不能互相污染。
- 规则/DNS 绑定变更后按需要使相关缓存失效；不能让旧 DNS 结果长期掩盖新策略。
- 代理 DNS 失败不自动降级到明文直连 DNS；同一信任边界内的候选切换必须明确。
- 节点启动 DNS 与目标 DNS 故障分别报告，不因某公共解析器失败重启全部代理。
- Static hosts、IPv4/IPv6 策略、DNS 测试及诊断应保留，但必须有对应的无 TUN 行为测试。

## 10. 订阅、导入与节点生命周期

### 10.1 导入产物不是只有节点

```text
源配置快照
   -> 节点及完整可支持选项
   -> 为获得节点所必需的 provider/来源关系
   -> 获取/流量/过期/UA 等元数据
   -> 被产品策略忽略的订阅分流内容清单
   -> 节点字段兼容性诊断及未映射内容
```

上游的 `keepDiversionRules`、`enableDiversionRules`、ISP 分流及订阅路由绑定不进入本项目领域状态。迁移器可以读取这些字段用于生成兼容性报告，但不会创建对应 RuleGroup，也不会把源内 selector/MATCH/FINAL 变成本项目路由目标。[S04]

### 10.2 格式支持策略

依次实现原生 sing-box、常见 URI、Base64/V2Ray 订阅、Clash/Clash.Meta，统一进入结构化节点与来源模型。每个格式维护节点字段级别兼容表：已支持、语义转换、明确不支持；路由/分流字段统一标记为“按产品策略忽略”.

协议参数如 TLS、SNI、Reality、传输、UDP、Mux、前置代理等不能通过只保留 `type/server/port` 的通用结构丢失。未知或不兼容参数产生路径级诊断。

节点导入有损必须可见。默认拒绝自动应用会破坏节点可用性的部分成功结果；用户必须看到丢失节点、字段与影响范围。订阅自带的路由规则、规则提供者和 ISP 分流属于明确的产品排除项，应单独列为“按策略忽略”，而不是混入解析错误；不能将“下载成功”显示成“节点更新完整成功”。

### 10.3 稳定更新流水线

```text
调度 -> 下载至暂存 -> 解码/解析 -> 差异与引用检查
     -> 编译/校验 -> 保存候选 revision -> 按策略应用
```

每个来源同一时刻最多一个更新任务。全局并发、下载大小、超时、重定向次数、解压大小、递归深度均有上限。使用 ETag/Last-Modified、退避与随机抖动，支持 429/Retry-After，不在断网时频繁请求。

分别记录 `last_attempt`、`last_success`、`last_error`、源版本和当前应用版本。错误不能更新“最近成功时间”。

空订阅、HTML 错误页、非法证书、部分响应、格式漂移、大量节点意外消失必须隔离。默认保留当前有效快照；清空现有节点需要显式确认，不能与远端临时错误混淆。

### 10.4 保留用户状态

更新不能覆盖用户手工设置的启用状态、节点别名、收藏、排序、分流目标、组 DNS、选择器偏好或源规则开关。

节点删除、重命名、凭据更换及同名冲突会影响自动组和固定目标，必须显示影响分析。失去唯一映射时不得“选一个同名的先用”。

### 10.5 CN 获取与恢复

支持明确的直接获取、经当前有效代理获取、用户选择的固定获取策略。Daemon 内部请求不得盲目继承 `HTTP_PROXY/ALL_PROXY`，防止控制 API、订阅下载或 DNS 引导绕回自身形成循环。

初次没有可用代理而订阅无法直连时，应提示导入本地文件或用户提供的可用入口；不能假装存在万能镜像。重启后先用持久化快照服务，再错峰更新。

## 11. 选择器、测速组与前置代理

### 11.1 保留独立实体

Global Auto、JP-Auto、US-Auto 等组可同时存在，组成员可来自多个订阅。显式节点选择和动态关键词/正则选择都要保留，匹配范围及合并语义用夹具确认。[S07][S15]

例如：

```text
Google       -> JP-Auto       -> 订阅 A/JP-02
OpenAI       -> US-Auto       -> 订阅 B/US-01
GitHub       -> CurrentSelected
哔哩哔哩     -> DIRECT
FINAL        -> CurrentSelected
```

修改 CurrentSelected 不能改变 JP-Auto、US-Auto 或固定节点的独立绑定；只有引用它的组受到影响。

### 11.2 避免双重调度和抖动

对同一自动组只能有一个权威选择算法。优先使用已经验证的内核 URLTest；Daemon 负责任务预算、显式测试和状态展示，不能再用另一套后台循环不断覆盖内核选择。

保留测试地址、间隔、容差、候选过滤、收藏偏好及健康检查的可配置能力。测试结果要区分未测、成功、超时、协议失败和检测端点异常，不能把 0ms 当成最佳节点。[S05]

自动切换需要容差、冷却和明确的失败阈值。测试端点整体不可达不能导致所有节点被永久删除。自动移除失败节点若提供，默认关闭，并有隔离/恢复机制及用户确认。

### 11.3 资源与网络代价

全局限制测速并发与请求速率；大量订阅的测速错峰进行，避免每次 TUI 重绘或进入页面就触发全量测试。动态 regex 使用受限、可取消的处理流程，输入长度与匹配规模有预算。

网络恢复后先做少量健康检查，再扩大测试，不同时刷新所有订阅和所有节点。

### 11.4 前置代理不是分流层

Karing 官方文档有前置代理能力；它描述的是实际网络拨号链，不是“规则组 → 自动组”的 UI 层次。[S15]

本项目在 P1 保留经过验证的用户态 detour/前置代理，形成独立出站依赖图。必须检测循环、缺失节点、链长及 DNS 引导依赖。不能为了实现代理链增加 TUN、netns 或系统路由修改。尚未支持的导入代理链必须明确阻止应用，不能丢弃 detour 后直连代理服务器。

## 12. 内核适配与控制接口

### 12.1 生产内核选择

Karing 设置中声明 `kCoreVersion = 1.14.0`，但这只是线索，不是发行二进制对应源码的证明。已检查的 `karing_v1.14.0` 候选包含 Karing 扩展；默认 `dev-next` 和其他 `karing_v*` 分支不能互相替代。[S05][S11][S13]

M0 必须产出内核锁定清单，至少包含：来源 URL、完整提交 SHA、补丁集、声明版本、Go 工具链、构建标签、依赖锁定、目标架构、二进制 SHA-256、测试矩阵版本和许可证。

候选 `go.mod` 写明 `go 1.25.5`；正式构建采用经验证、受维护的精确工具链版本。不能把这个候选要求误认为本项目已完成工具链选型，也不能从 `github.com/sagernet/sing-box@latest` 意外构建成另一份内核。[S11]

### 12.2 控制能力表

| 功能 | 方案 | 必需验证 |
| --- | --- | --- |
| 启动/停止 | Daemon 子进程监督 | 退出码、超时、回收、所有权 |
| 完整配置变更 | 编译验证后受控重启/回滚 | 不依赖 PUT /configs 的空成功 |
| 当前选择切换 | 经验证的 selector API | 回读选中值、持久化意图、重启恢复 |
| 模式切换 | API 能力与生成规则共同实现 | 仅 PATCH mode 不一定代表全部语义生效 |
| 日志/流量/连接 | 经过验证的流接口 | 格式、帧大小、重连、取消、关闭 |
| 测速 | 经验证的 API/URLTest | 目标含义、超时、并发与结果解释 |
| DNS/规则状态诊断 | 按候选能力提供 | 无接口时明确显示不支持，不伪造结果 |
| Karing 扩展 | 独立 capability | 不假设标准 Clash 服务都有 `/karing` 的行为 |

所查候选的 `GET /configs` 也不是完整运行配置的权威导出；配置审计应使用自身生成代际和能力回读共同完成。[S13][S14]

### 12.3 运行和升级边界

不得让自动升级替换运行中的唯一内核文件。应用、内核、配置 schema、rule-set 格式应形成经过测试的组合。

结构变更默认允许短暂受控中断，必须显示影响。没有验证内核支持时，不承诺无损热重载；已有 TCP/UDP 会话在内核重启后可能中断。节点选择切换默认不主动关闭旧连接，新旧连接去向差异应可解释。

健康检查分为本地进程/控制面、入口可用性、目标网络可达性。外网不可达不应被当作配置结构损坏来反复回滚。

## 13. 配置事务、应用与回滚

### 13.1 不可变代际

运行文件不是唯一真相，领域状态也不能在网络请求中边解析边覆盖。

每个代际包括声明状态版本、编译结果、source-map、规则清单、适配器版本、内核锁定以及校验记录。已被运行或标记为 last-known-good 的代际不可原地修改。

### 13.2 应用流程

1. **建立候选**：基于指定 revision 应用变更，完成字段、引用、布尔语义、能力与资源检查。
2. **生成暂存代际**：写入完整文件、校验内容哈希，刷新文件并以同文件系统原子重命名发布资源目录；需要持久恢复的目录也执行相应同步。
3. **内核检查**：使用该代际绑定的同一内核执行配置 check，使用本地规则和明确路径，限制执行时间。不能只用 JSON 语法检查代替内核检查。
4. **记录意图**：持久记录 pending application、旧 applied 代际与恢复信息；持久化失败时不停止健康 core。
5. **受控应用**：暂停冲突写入，按既定超时停止旧 core，启动新代际。候选测试不得共享并破坏运行缓存文件。
6. **确认健康**：验证进程、认证后的 API、预期端口及必要的本地代理行为。网络探测另行分级，避免断网误判本地配置失败。
7. **提交应用状态**：持久记录 applied generation，再更新观测状态；成功观察后按策略提升为 last-known-good。
8. **失败回滚**：启动上一有效代际及对应内核、资源和选择状态，报告失败原因，不默默显示新配置已成功。

配置文件、SQLite 和实际进程不能组成一个天然的原子事务。因此需要显式应用日志和崩溃恢复规则，不能仅以“用了数据库事务”宣称跨系统一致性。

### 13.3 崩溃恢复规则

- 仅声明状态存在、代际未完整写入：保留为草稿，不作为运行配置。
- 代际完整但 check 未通过：不应用。
- pending 已记录但 applied 未确认：启动恢复时优先已确认有效代际；候选是否继续需明确恢复策略。
- 新 core 已启动但提交应用状态前崩溃：用 journal、代际标识与进程身份判定，不能仅看端口占用就接管。
- 新代际确认失败：回退旧代际；旧代际也无法运行则进入 Failed，而不是生成全直连配置。
- 用户明确停止：恢复后维持停止意图，除非存在经确认的新启动命令。

以上每个持久化/停止/启动边界都要有故障注入测试。

### 13.4 选择状态与缓存

节点选择变化也需要 revision 或独立版本号、回读和持久记录。API 调用超时时结果可能不确定，必须回读后协调，不能盲目重复并覆盖更新的选择。

内核缓存是运行数据，不得比领域设置更有权威。新代际与回滚要验证恢复后的模式和选择；缓存 schema 变更单独处理，不让新内核破坏唯一旧缓存。

### 13.5 保留与回收

至少保留当前有效代际及上一有效代际，建议默认保留最近 5 个已确认代际并设置磁盘配额。活动、pending、回滚和备份仍引用的内核及规则资源不能被垃圾回收。

磁盘空间不足时优先拒绝新事务，继续服务现有配置；不得为了给更新腾空间删除唯一可恢复版本。

## 14. 安全边界

### 14.1 本地访问

默认管理 API 使用 Unix Domain Socket，目录 0700、socket 0600，检查同 UID 对端。Core 控制接口限定 Loopback，使用随机高熵 secret，即使监听本机也不能关闭认证。

本项目防止其他普通用户未经授权操作；同 UID 的恶意进程仍属于信任边界限制，不将本地权限控制夸大为强隔离。

Native HTTP/WebSocket 客户端使用 Authorization Header，不把 token 放进 URL、命令行或日志。所查内核支持 Header 鉴权，无需沿用浏览器的查询参数 token 方式。[S13]

### 14.2 非可信输入

订阅、规则文件、ZIP、节点名称、日志、服务端返回值都视为非可信输入。必须验证：

- JSON/YAML 类型、重复键、别名扩展、大小、嵌套深度、节点数量和规则数量。
- URI、重定向及嵌套规则下载目标；跨源跳转不得泄漏原请求凭据。
- 订阅触发的私网/本地资源访问需遵循显式来源许可，防止把任意远程配置变成本机网络探测器。
- ZIP 路径穿越、绝对路径、链接文件、压缩炸弹与不允许的内容类型。
- 配置不能指定任意可执行程序、Shell 片段、特权设备、系统目录或不受允许的监听入口。
- TUI 对 ANSI/OSC 控制序列进行处理，防止恶意节点名或日志改变终端状态、伪造提示或操作剪贴板。

### 14.3 凭据与隐私

订阅 URL、密码、UUID、私钥、WebDAV 凭据、DNS 中的用户标识和完整访问目标不进入普通日志。错误展示使用脱敏摘要，诊断包默认不包含原始订阅与运行密钥。

敏感文件使用用户私有目录与 0600 权限；这不是磁盘加密。需要加密备份时使用经过审查的现成实现，不自创密码学协议。

默认关闭遥测、崩溃自动上传、详细访问历史和对外诊断端口。不得把原版 Sentry/推广集成作为运行依赖。

### 14.4 TLS 与例外

管理请求、订阅、更新及同步必须验证 TLS。节点本身要求 insecure 等例外时，应按具体节点明确展示并经用户确认；不能因为失败就全局关闭证书验证。

## 15. 资源预算与可靠性目标

### 15.1 目标定义

以下是初始验收预算，不是实测结果。M0 建立基准，后续修改需给出测量和 ADR，不得在出现泄漏后简单提高上限来过关。

参考负载：10 个订阅、1,000 个节点、30 个策略组、CN 全预设资源在磁盘可用、默认 6 组生效，256 条受控活动连接；amd64/arm64 各至少一个 2 核、2 GiB 级别的测试环境。吞吐另做独立基准，不用外部服务波动掩盖本地资源问题。

| 指标 | 初始目标/预算 |
| --- | --- |
| Daemon 稳态 RSS | 不超过 128 MiB；高负载峰值另报告 |
| 单个 TUI 稳态 RSS | 不超过 128 MiB；退出后资源释放 |
| Core 内存 | 参考负载先以 512 MiB 为评审预算，M0 按真实协议/规则集测量确认 |
| 空闲管理面 CPU | Daemon 长窗口平均低于单核 1%；TUI 限制重绘，不忙轮询 |
| 流量显示 | 默认约 1 秒更新；不因高频事件无限重绘 |
| 本地普通状态查询 | 参考负载下 P95 小于 200ms；慢客户端不能阻塞核心写入 |
| Core 单次崩溃恢复 | 无熔断、有效本地资源时，目标 30 秒内恢复本地就绪 |
| 非法配置更新 | 100% 不替换有效运行状态；持久化失败发生在停止旧 core 之前 |
| TUI 退出/异常 | 不导致 core 重启或已有代理连接被主动关闭 |
| 长期测试 | 72 小时持续集成候选、7 天压力/故障混合测试、30 天正式发布候选运行 |

内存预算不是对所有协议、节点规模和终端大小的承诺。规模超出已验证范围要提示、限流或拒绝新任务，不能静默丢配置。限额不是触发频繁杀死健康 core 的理由。

### 15.2 所有队列和缓存有界

建议初始控制值：订阅下载并发 2、显式测速任务并发 8、日志 UI 环形缓冲最多 2,000 行且不超过 8 MiB、单次配置/订阅解码前 16 MiB/解码后 64 MiB、普通控制请求超时 5 秒、下载总期限 60 秒。

这些限额应是命名配置，不是到处散落的常量。需要大订阅时允许在可见预算下调整；达到上限必须返回明确诊断，不截断后当完整配置应用。

Core 内部 URLTest 并发不受外部 Go 队列自动约束，必须单独核实和测试。连接观测快照可以分页或限制显示，但不能因此关闭实际业务连接。

### 15.3 日志与磁盘

默认记录生命周期和可操作错误，不长期运行 trace。应用与内核日志都要轮转；可用初始配额为每类 5 个 10 MiB 文件。重复故障聚合计数，避免断网时刷盘。

统计数据默认按有限时间窗口聚合，详细连接历史默认关闭。缓存、下载暂存、旧代际和备份都有独立配额与回收策略；清理不得删除仍被引用的文件。

### 15.4 长期无泄漏要求

以预热后的状态为基准记录 RSS、FD、goroutine、任务数、缓存条目与磁盘占用。长时运行不应随 TUI 连接次数、订阅更新次数或 WebSocket 重连次数线性增长。

至少完成 1,000 次 TUI 连接/断开、观察页切换和流重连循环，结束后 FD/goroutine 回到合理基线范围。7 天曲线的持续增长必须解释并修复；不能通过每日定时重启来代替修复。

### 15.5 故障隔离

外部下载、DNS、测速、同步、UI 观测各自有取消、退避与错误边界。日志、统计或 WebDAV 失败不能停止代理。

如果磁盘只读或写满，服务进入明确的只读管理状态，尽量保留现有 core；新配置与自动升级暂停。数据库不可恢复时不能悄悄初始化空数据库覆盖旧文件。

## 16. 可观测性与故障诊断

### 16.1 状态不能只显示 Connected

至少展示：Daemon 是否响应、core 进程状态、控制 API 状态、Rule 入口状态、当前目标、目标最近测试时间、网络健康、配置 desired/applied revision、内核与规则版本、数据是否过期。

进程 Running 不等于代理目标可达；最近一次测速成功也不等于所有网站可达。无法确认时显示 Unknown/Degraded，而不是绿色“已连接”。

### 16.2 指标

记录启动/重启原因、失败计数、退避状态、配置应用/回滚次数和耗时、订阅最近成功时间、规则包新旧版本、任务队列长度、观察消息丢弃数、磁盘配额和资源使用。

Debug/pprof 只在显式诊断模式启用，并限制本地访问与有效期。指标标签避免使用完整域名、订阅 URL 或节点凭据，以免产生隐私与高基数问题。

### 16.3 分流解释

诊断输出至少包含：输入域名/IP/端口/网络、是否经过 Rule 入口、运行模式、匹配层、源组、规则、目标引用、自动组实际节点、DNS 策略、运行代际。

`route explain` 的离线推演必须标注“模拟”。没有 IP、嗅探信息或进程信息时列出未知条件，不能把模拟结果当作已经发生的真实连接事实。官方文档也指出仅用域名检测可能与实际流量结果不同。[S15]

实际连接信息优先使用 core 暴露的观测，结合 source-map 解释。Core 不提供的阶段数据应显示 unavailable，不能补造一条看似完整的链路。

### 16.4 运维手册

在正式发布前提供 runbook：启动失败、端口冲突、认证失败、规则过期、全节点测试失败、DNS 循环、磁盘满、回滚失败、SSH 后台生命周期、订阅突然清空、恢复备份等场景，都要有检查顺序和不会破坏有效状态的处理办法。

## 17. TUI、CLI 与本地 API

### 17.1 页面

| 页面 | 内容 |
| --- | --- |
| Dashboard | 分离展示服务、core、入口、网络健康和 applied generation |
| Profiles | 多订阅、流量、来源、节点过滤、更新策略、被忽略的订阅分流摘要和错误 |
| Proxies / Groups | 节点搜索、收藏、显式选择、自定义自动组、动态成员与测试状态 |
| Routing | 按五层展示组、开关、顺序、目标与 DNS；标明 CN 预设及自动追加来源；不存在订阅/ISP 分流层 |
| DNS / RuleSets | 分层 DNS、组覆盖、资源来源与版本、离线状态、更新预览 |
| Connections / Logs | 过滤、来源映射、连接关闭、有限日志流及脱敏 |
| Settings / Diagnostics | 配置预览、应用、回滚、备份、核心能力与故障报告 |

### 17.2 操作约束

`q` 和普通 Ctrl-C 默认只退出 TUI。停止整个代理必须是明确操作，并显示影响；不能用容易误按的全局按键无提示终止 daemon/core。

多层分流页不能退化为平面开关列表。每组编辑必须同时显示匹配来源、目标、DNS、有效状态和遮蔽提示；跨层移动应受规则限制，不允许拖动后无提示改变来源语义。

网络和磁盘操作异步进入服务任务；Bubble Tea Update/View 不进行阻塞 IO。支持终端缩放、窄屏、键盘操作、中文、无 emoji 模式，以及安全恢复终端状态。具体 Bubble Tea 版本在 M0 锁定，不混用不同大版本 API。[S25]

### 17.3 拟定 CLI

以下是设计接口，不代表当前仓库已经提供这些命令：

```text
karing-tui tui
karing-tui daemon run
karing-tui core status|start|stop
karing-tui profile import <file> --dry-run
karing-tui profile update <id>
karing-tui config validate|diff|apply|rollback
karing-tui group list|show|select
karing-tui route explain --domain <name> --port 443 --network tcp
karing-tui rulesets status|update
karing-tui backup create|inspect|restore
karing-tui doctor
karing-tui env
```

非交互命令提供结构化 JSON 输出、明确退出码、超时与无 secret 错误信息。脚本不得依赖 TUI 文案解析。

### 17.4 本地 API 契约

使用版本化 Unix Socket API。最小能力包含 status/capabilities、配置预览与应用、订阅操作、组选择、任务查询/取消、事件流。

写入带 `expected_revision`；长任务返回 JobID。重试需要有界幂等键，配置冲突明确返回 conflict。事件包含序号和快照版本，断线后先重新取快照再订阅；不建立无限历史事件队列。

### 17.5 应用接入说明

可以提供下列环境变量示例，但 `env` 默认只输出，不擅自写用户文件：

```sh
export http_proxy=http://127.0.0.1:2080
export https_proxy=http://127.0.0.1:2080
export all_proxy=socks5h://127.0.0.1:2080
export no_proxy=localhost,127.0.0.1,::1
```

变量是否生效取决于应用；浏览器等可能有自己的代理与 DNS 设置。`socks5h` 表示向代理传递 hostname，不表示无条件在国外解析。`no_proxy` 绕开的流量不进入本工具的分流或连接统计。curl 的 HTTP 代理环境变量应使用小写形式。[S26]

## 18. 持久化、备份与同步

### 18.1 目录

遵循 XDG 路径，并允许显式覆盖；不能硬编码假设用户都使用同一个 home。[S20]

```text
$XDG_CONFIG_HOME/karing-tui-v2/        启动配置、机器级路径与策略
$XDG_DATA_HOME/karing-tui-v2/          固定版本 core、规则和上游预设资源
$XDG_STATE_HOME/karing-tui-v2/         权威状态数据库、代际、应用日志、备份
$XDG_CACHE_HOME/karing-tui-v2/         可再生下载暂存、有限缓存
$XDG_RUNTIME_DIR/karing-tui-v2/        socket、锁、瞬时运行标识
```

无 `XDG_RUNTIME_DIR` 时，使用经所有权和权限验证的显式运行目录，或给出设置指导；不直接创建所有人可写的固定 `/tmp` socket。

### 18.2 存储策略

建议使用 SQLite 作为领域状态的唯一权威存储，daemon 单写入者，版本化 schema 和迁移。Bootstrap 文件只管理启动环境，不与数据库中的规则、选择器和订阅形成两套权威配置。

完整配置通过 export/import 编辑或迁移。直接修改运行代际文件不是受支持的配置方式。

启用 WAL 时要限制长事务、读事务寿命、checkpoint 与 busy timeout。数据库部署在经过支持的本地文件系统上，不能默认允许网络文件系统上的 WAL。具体驱动、CGO 与发行方式在 M0 评估锁定。[S24]

### 18.3 自有备份

备份包含 schema、应用版本、声明状态、资源引用清单、完整性校验和是否含凭据的标记。数据库采用一致快照接口，不能只复制正在运行的主数据库文件而忽略 WAL。[S23]

恢复顺序：检查来源与格式 → 安全解包 → 完整性校验 → schema 迁移 → 引用/资源/内核兼容检查 → 展示差异 → 经正常应用事务生效。

备份不意味着无条件可执行导入内容，也不能覆盖原始备份。敏感备份应支持现成加密格式；明文导出需提示并使用私有权限。

### 18.4 Karing 数据迁移

P1 支持从用户提供的 Karing 备份或导出文件只读迁移。由于关键备份工具和模型转换代码在已审查公开快照中不完整，不能提前保证任意版本 ZIP 都可导入。[S03][S04]

迁移报告逐项列出保留、映射、忽略的平台字段和不支持内容；不在 Karing 原目录中修改文件，不让两套程序同时写同一份数据。

### 18.5 同步

WebDAV 和 LAN 同步是显式可选功能。WebDAV 使用版本/ETag 与冲突检测，不能简单以最后写入覆盖本地活动配置。远端变更先成为候选，经同样验证与事务后应用。

LAN 同步不默认公开监听或无认证发现。认证、权限、传输保护和内容限额先完成，再实现自动化体验。同步故障不影响已运行的本地代理。[S28]

## 19. 构建、发行与升级

### 19.1 可复现与来源

锁定 Go 版本、模块依赖、构建标签、生成器、分析器、打包工具与 CI Actions 提交。不能只锁定仓库 SHA，然后仍调用 `@latest` 工具；所查内核 Makefile 正存在这类调用，需用可审计的固定构建流程替代。[S12]

发行产物记录应用 commit、core commit/patches、preset commit、规则 manifest、工具链和目标架构，提供 SHA-256 清单与 SBOM。二进制一致性无法做到时，必须记录非确定因素，不虚构可复现结论。

### 19.2 Linux 支持矩阵

先验证 amd64、arm64 的 tar 包和普通用户目录安装。明确 libc、内核和 CPU 指令集要求；不要直接继承原 Flutter Linux 包的 glibc 下限，也不要未经测试承诺静态二进制适用于所有发行版。[S01]

CI 必须包括真正可执行的架构测试，不能把交叉编译成功当作 arm64 运行通过。无 DISPLAY、无 GPU、无桌面 keyring 的环境应可运行核心功能。

### 19.3 版本升级

应用、core、资源升级先检查组合兼容性并保留旧版本。重大 schema 迁移前创建一致备份；回退应用时要么能读取 schema，要么恢复旧快照，不能要求旧程序强行读取新数据库。

默认不在用户工作期间自动升级并重启 core。更新检查、下载、校验、应用是不同动作；规则更新也不等于可以原地覆盖运行资源。

### 19.4 许可与名称

Karing 基线许可证声明 GPL-3.0-or-later，并包含未经同意不得使用名称或暗示关联的文字。正式发布前要核实应用代码、内核、规则数据、字体/图标及依赖的许可和署名义务，准备相应源码与修改记录。[S10]

`karing-tui-v2` 暂作为当前仓库工作名称。是否使用 Karing 名称发布，应取得许可或确定其他合适名称；本计划不自动重命名仓库，也不把命名问题当作已解决的法律结论。

## 20. 测试与验收矩阵

### 20.1 测试层次

单元测试覆盖模型、排序、开关、引用、布尔表达式和编译；属性测试覆盖确定性、等价性和不变量；模糊测试覆盖格式导入、规则表达式、ZIP 和配置；集成测试运行固定 core 与本地受控 DNS/代理服务；最后进行真实环境与长期运行测试。

测试数据不得包含真实订阅 token、私人节点密码或用户浏览记录。外部公共服务不应成为普通 CI 是否通过的必要条件。

### 20.2 兼容夹具

每个夹具至少记录 Karing 应用来源/版本、内核来源或可验证指纹、输入配置、用户设置、规则资源哈希、平台/无 TUN 模式、预期配置语义与实际请求结果。

通过同输入对照 Karing 导出/运行行为与本项目结果。比较时只规范化无关路径、随机标识及对象键；不能排序规则数组或删除有实际语义的 DNS/出口字段来制造“相同”。

源码确认只能覆盖一部分行为。没有参考运行结果的项标注 `source-reviewed / behavior-unverified`，不得算作通过的兼容项。

### 20.3 必需验收案例

| T20 | 大量日志、慢客户端、1,000 次流重连 | 队列/内存有界，core 不因管道阻塞停顿，FD/goroutine 回归基线 |
| T21 | 非可信导入、ZIP 路径、控制序列、secret | 不能越权写入或执行；日志、URL、诊断与 TUI 不泄漏凭据 |
| T22 | HTTP、SOCKS hostname/IP、所声明 UDP 能力 | 协议分别实测；不支持的能力明确返回错误 |
| T23 | 一致备份、迁移、同步冲突、旧版本恢复 | 恢复前验证且可回滚，不复制损坏的运行 DB，不静默覆盖本地状态 |
| T24 | amd64/arm64 离线发行包 | 断开下载源后已有配置可启动；所需规则、core 与来源清单齐全 |
| T25 | 72h、7d、30d 长期运行 | 无未解释持续增长、无重启风暴、无状态损坏和规则旁路 |
| T26 | 规则模拟与真实连接解释 | 区分 unknown/simulated/observed，输出包含源组及代际，不能伪造命中链 |

### 20.4 稳定性试验内容

长时测试应交替包含正常流量、大文件传输、连接抖动、订阅更新、规则更新、组切换、TUI 重连、DNS 超时、节点全部不可达、core 非正常退出和可恢复的磁盘压力。

每次试验保存资源曲线、应用日志、配置代际、重启原因和故障恢复结果。7 天与 30 天验收不是“进程没退出”就通过，还必须证明分流、选择与 DNS 在多次变更后仍正确。

CI 启用 Go race 检查和取消/超时测试。内核不可通过 Go 应用 race 自动覆盖，需要独立集成与压力测试。新的缺陷必须变成回归夹具后才能关闭。

## 21. 开发阶段与发布门槛

不以固定日期承诺完成度。每个阶段以可验证产物为门槛，未过门槛不得跳到正式兼容声明。

### M0：基线、兼容契约与风险消除

产出：源码证据表、公开依赖缺口、字段兼容矩阵、内核来源与构建锁定、许可清单、CN 资源清单、关键未知语义夹具、ADR 和测试环境说明。

必须先验证内核 CLI 普通用户运行、Clash API 实际能力、SRS 格式和各架构基本可执行性。确认 Bubble Tea、SQLite 驱动、Go 与构建工具的精确版本。

**门槛：** 不再把默认分支等同于生产内核；对配置重载、五层顺序、订阅分流剥离边界、组 DNS、地区追加、平台字段布尔语义有可执行验证方案和首批参考结果。仍不确定的 P0 行为登记为阻塞项。

### M1：稳定服务底座

实现 daemon、单实例、用户服务配置、日志限额、状态数据库、代际与应用 journal、core 监督器、三个入口、原生配置的受限导入和本地健康检查。

优先完成 T01、T14、T15、T17、T18、T19、T20 的骨架测试。TUI 此阶段可以只有状态页或 CLI，不能让界面开发掩盖后台基础缺失。

**门槛：** 错误配置不能破坏有效 core；停止意图能恢复；TUI 消失不停止代理；这是内部原型，不称为完整 Karing 终端版。

### M2：完整分流与 DNS 核心

实现五层 IR（自定义 → GeoSite → GeoIP → ACL → FINAL）、独立开关、全部目标类型、CN 28 组、地区追加、自定义测速组、每组 DNS、来源映射和语义校验。

完成 T02–T13、T26 的核心夹具，并通过实际 core 的请求结果验证。未知的 P0 规则/DNS 语义必须解决，或明确阻止相应输入且不能宣称完整兼容。

**门槛：** 不接受“暂时只有 CN 直连和全局代理，后面再补多层”的替代验收。多层机制是核心，不是后期增强。

### M3：订阅与长期调度

实现格式转换、完整节点来源模型、节点对账、订阅分流剥离报告、UA/获取策略、流量信息、定时更新和有限测速。

完成空/损坏/部分更新的隔离，节点增删对规则绑定的影响分析，测试调度与网络恢复去抖。逐协议、逐格式更新兼容矩阵。

**门槛：** 订阅更新不损坏用户状态，不把订阅/ISP 分流注入五层路由树，不产生静默节点字段丢失、旁路或无界后台任务。

### M4：完整终端操作与恢复能力

完善 TUI 各页面、CLI、版本化 API、配置差异预览、真实/模拟分流解释、一致备份恢复、doctor 和 runbook。

完成恶意终端内容处理、窄屏和中文显示、多客户端冲突、敏感信息脱敏。

**门槛：** 普通用户可以不编辑运行 JSON，完成订阅导入、组选择、规则/DNS 调整、状态查看、故障定位和回滚。

### M5：发行候选与长期稳定性

完成两种架构发行、来源清单、升级/回退测试、无网络启动验证；运行 72 小时、7 天、30 天测试并归档证据。

修复所有 P0 缺陷和未解释资源增长。调优后重新运行受影响的兼容与稳定性测试，不能用定时重启或清空配置绕过问题。

**门槛：** T01–T26 全部满足所声明范围，无未解决的核心分流/DNS/恢复缺陷，名称与许可发布条件已经处理。只有此时才能发布首个正式稳定兼容版本。

### M6：持续增强

按独立 ADR 和测试补充前置代理、Karing 备份迁移、WebDAV/LAN 同步、高级统计、二维码及其他用户态能力。每项增强都必须遵守普通用户权限、无静默降级、资源有界和可回滚的相同标准。

## 22. 风险登记与停止条件

| 风险 | 等级 | 对策及停止条件 |
| --- | --- | --- |
| 公开关键模块缺失，误猜运行语义 | 高 | 用固定版本参考运行与夹具补齐；核心语义未验证时不宣称完整兼容 |
| 选错内核分支或工具链漂移 | 高 | 固定来源、构建工具和能力清单；不能复现/来源不明则禁止发行 |
| 分流或 DNS 隐式直连泄漏 | 高 | 缺失引用失败关闭相关变更，实际 DNS/出口测试；有旁路缺陷立即阻止发布 |
| 更新破坏唯一有效状态 | 高 | 不可变代际、journal、LKG、故障注入；恢复不确定则不自动继续更新 |
| 订阅分流意外进入运行时路由树 | 高 | 领域模型不提供订阅/ISP 层；导入统一剥离 rules/MATCH/FINAL/rule-provider 路由绑定并用 T12 回归测试 |
| 重启、测速或下载风暴 | 高 | 单一调度所有权、预算、退避、熔断；外网故障不等于进程故障 |
| 多客户端和自动任务竞态 | 高 | 单写入者、revision/CAS、幂等命令、事务串行化 |
| 规则资源在 CN 不可下载 | 中高 | 随包离线闭包、可信来源、保持旧代际；下载不是启动前提 |
| Linux 进程信息不可用 | 中 | 明确 Unknown，平台条件安全处理，不提权和不删条件造成全匹配 |
| 日志/历史无限增长 | 高 | 内存/磁盘双限额、轮转、聚合、长时曲线验收 |
| 名称或规则数据许可不清楚 | 高 | 发布前确认授权/合适名称和数据许可证，不自动假定 GPL 涵盖全部资源 |
| 用户服务在注销后退出 | 中 | 明确 systemd/linger 条件并测试，不能把会话前台进程包装成永久服务 |

### 2026-10-09 M4 当前声明显式应用的校验回执切片

- 新增 `GET /v1/config/apply/preview`：在 daemon OperationGate 中读取未应用的**当前声明头**，核对声明 SHA 与配置修订、已应用代际、CurrentSelected 修订，重新严格编译并返回无敏感内容的原生 SHA-256/规则资源统计；不进行真实 core check 或运行态变更。
- 新增 `POST /v1/config/apply/confirm`：接收预览签认的固定标识与原生哈希，在同一 Gate 内复验、重新编译，调用既有原子代际应用协调器完成 `check -> activate -> verify -> commit`，失败交由既有 journal/rollback/recovery。冲突回执不得再应用；超时/断链不盲重试。
- CLI 提供 `config apply-preview [--out=0600_FILE]`、`config apply --receipt=PRIVATE_FILE --confirm`，拒绝 symlink、非私有/非本人文件、失效摘要或缺少明确确认；成功后校验代际与配置修订回读。应用可能替换 core 并影响连接，不因预览或 TUI 页面切换而自动发生。
- 当前仅是 **CLI 当前头版本应用闭环**，不能宣称 TUI 版本回滚、历史代际主动恢复、一致性备份或 M4 完成。五层路由/CN 预置/订阅 ISP 排除、Linux 普通用户和无 TUN 不变。详见 ADR 0082。

### 2026-10-09 M4 已确认历史代际只读完整性审计切片

- SQLite 按成功 `committed` 的 journal + archived history 生成有界（最多 12 条）去重代际目录，记录已持久化修订号与 payload 是否被 retention 清理，绝不把 prepared/rolled_back/failed 候选当作可恢复配置。
- 新增 `GET /v1/config/recovery/audit` 和 `config recovery-audit` 只读入口：逐代际复核原生配置、manifest、source-map 的 SHA-256 与 JSON、原生 schema、声明 revision/hash 及声明本体，并对 manifest 指向的私有 content-addressed 规则资源复用 no-follow/owner/hash 验证；禁止将任意存储路径当作规则文件打开。
- 返回只有脱敏状态枚举、代际、修订号及完整性布尔值；配置、DNS 上游、节点密钥、rule-set 路径或原始错误不输出。状态与声明在采集前后变化则 409 拒绝拼接快照；资源已经清理或损坏时标记不可用，不悄悄回退为直连。
- **所有 `restore_ready=false`，`restore_supported=false`**：哈希验证仅说明存储内容与规则文件在该时刻可核查，并不代表该历史配置现在可应用。手动历史代际回滚必须先补齐 CurrentSelected/运行路由策略绑定、规则资源闭包的应用时再校验、可恢复代际 CAS、内核严格检查/事务激活与故障注入测试，不能绕过保护直接复用历史 native JSON。见 ADR 0084。


### 2026-10-09 M4 历史代际严格编译与内核 Check（无激活）切片

- 在 ADR 0084/0085 的只读历史审计和 ADR 0086 的 SQLite 原子候选准备基础上，新增仅供 daemon 内部调用的 `CheckHistoricalGeneration`。不注册 HTTP、CLI、TUI 或能力开关，不允许终端直接触发历史配置替换。
- 在与 core 生命周期和配置应用共享的 OperationGate 内，先核查成功提交的历史代际和当前应用/LKG 资源闭包、CurrentSelected、routing mode 与目标状态；旧声明必须由**当前编译器及控制面参数**重新编译，要求原生 JSON、manifest、source-map 和历史存档逐字节一致。
- 单个 SQLite CAS 事务将历史代际复制为新候选，使用现有 journal/配额/崩溃恢复机制；只调用 core.Check，不进入 activate/verify/commit。检查后即使连接取消或 core.Check 失败，也以独立清理超时回收 prepared 活动槽，检测变更/回收失败时报错；成功回执永远不表示可恢复。

### 2026-10-09 M4 历史恢复规则资源 inode 钉住检查切片

- 在仅 daemon 内部执行、无激活的历史代际 core Check（ADR 0087）中，针对目标代际与已应用/LKG 回退代际，建立去重且受文件数/累计字节预算约束的源/二进制规则集文件句柄。
- 打开时坚持 content-addressed 私有根目录、Linux no-follow、普通文件、属主、权限及 SHA-256；Check 前后在**同一打开文件描述符**上核查哈希、大小、权限及路径是否仍指向原 inode，拒绝“同内容新 inode 替换”。
- 同时对历史目标、当前应用及 LKG 在 SQLite 中的原生 JSON、manifest、source-map 的内容与 SHA-256 作前后快照对比，拒绝检查过程中的回退代际元数据变化，并确保检查结束撤销 prepared 活动 journal。
- 此改进仍只是进程内检测：无法凭文件描述符阻止路径短暂替换再还原（ABA），不代表已经获得真实激活期间的资源租约，更不支持手动恢复。下一步仍需隔离恢复资源、核验与激活之间的状态/权限锁、双层回滚故障注入及一致备份；M4/T15/T23 未验收。详见 ADR 0088。


### 2026-10-09 M4 历史配置 Check 候选空间回收切片

- 在 ADR 0086–0088 的内部安全检查基础上，修复重复检查可造成 SQLite `generations` 已失败候选积累、耗尽保留预算的问题；禁止以宽泛的历史清理来换取恢复检查空间。
- 检查成功、失败或取消时，先使用独立超时将 prepared journal 标记为明确的未激活检查失败，再在**单个 SQLite 事务**内验证恢复来源、专用标记、无活动状态、无 recovery_required、无其他 journal/history 引用、不属于 applied/LKG，归档失败记录后仅删除这一失败候选的存储 payload。清理出错仍是硬失败，不会激活 core。
- 测试覆盖重复检查、配额紧张、历史 tombstone 保留、普通失败应用/回滚失败/中断恢复和其他代际引用均不可误删，防止因只读兼容检查影响长期运行正常配置写入。进程在清理前崩溃时依赖既有 recovery/retention 清理遗留候选。
- **仍不开放手动恢复或备份恢复**；继续优先实现隔离的不可变运行规则文件快照、跨重启租约、故障注入验证的双层回滚。M4/T15/T23 及长时间稳定性门槛尚未关闭。详见 ADR 0089。


### 2026-10-10 M4 隔离规则资源快照（仅历史兼容检查）

- 在 ADR 0088 的规则文件句柄钉住、ADR 0089 的检查候选回收基础上，新建只供 daemon 内部调用的隔离副本构建器 `coreartifact.StagePinnedRuleSetSnapshot`：对历史目标、当前已应用和 LKG 的规则文件闭包去重，限定 128 个文件、128 MiB 总量以及单个 64 MiB 上限。
- 从此前已校验并保持打开的文件描述符复制，**不是硬链接**：复制前后重查来源 inode 与哈希；以私有随机目录、独占新文件、`0400` 权限、文件及目录 fsync 形成检查期临时副本。内核 Check 前后核对副本和来源，检测路径替换、内容和权限变化；成功/失败/取消均定向清理并拒绝清理未知文件或被替换目录。

- 无手动恢复 HTTP/CLI/TUI，无核心激活；`restore_supported=false`、所有 `restore_ready=false`，T15/T23/M4 未验收。参见 ADR 0090。
