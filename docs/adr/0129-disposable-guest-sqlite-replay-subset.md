# ADR 0129 — Non-authorizing disposable-guest SQLite replay subset comparison

- **Status:** M4 experimental, read-only; neither T15 nor T23 is accepted by this ADR.
- Builds on ADR 0128's guarded host-side virtual guest stop. Does not enable restoration, metadata deletion, automatic GC, actual Core Activate/Verify, TUN or external file IO on a user's ordinary host state.
- Environment remains Linux non-root, CN preset 28 groups, original Custom → GeoSite → GeoIP → ACL → FINAL layering and exclusion of subscription/ISP routing.

## Problem

A successful `virsh destroy` witness records only a forced virtual guest stop. It cannot prove that the deliberately interrupted SQLite/journal, Applied/LKG generations, selection and Core intent survived re-entry, and does not certify virtualized storage as a power-cut equivalent. The next controlled slice should inspect actual **guest-side** SQLite state after an operator starts the throwaway VM, rather than trusting opaque self-reported "recovered" checkboxes.

## Decision

1. Add `scripts/recovery_lab/guest_reboot_audit.py` to execute **inside only a disposable non-root test guest**, with a dedicated `$XDG_STATE_HOME/karing-tui-v2/state.db` and the same fixed per-nonce `recovery-lab/ktui-powercut-disposable-<nonce>` private witness directory. Its explicit `KTUI_LAB_GUEST_AUDIT_ACK=GUEST_AUDIT:<domain>:<uuid>:<case>:<nonce>` acknowledges this guest-only lab, **not** power-loss/restore approval. Reuse ADR 0128's exact disposable VM name, canonical UUID, nonce and four eligible checkpoint cases.
2. `--mode capture` (before the experimental checkpoint) reads actual SQLite state using the Python built-in SQLite driver in `file:...?mode=ro` with `PRAGMA query_only=ON`, never `immutable=1` (which could disregard WAL), and stores one new owner-only `0600` fsynced and parent-fsynced JSON baseline. The baseline includes only a fixed allowlist of metadata counts, generation digests and booleans; it never exports original config payload, node credentials, SQL errors or paths. Print the baseline file's SHA-256, which the operator must retain **outside** the guest; an unkeyed local SHA is not anti-malicious attestation.
3. Refuse a non-owned, non-private, symlinked, hard-linked, missing or over-64-MiB SQLite file; pin the path/inode before and after reading, and bound individual witness documents to 16 KiB. Accept SQLite current schema **exactly v18**, complete ordered migration numbers 1–18, `PRAGMA integrity_check(1) = ok`, empty `foreign_key_check`, exactly one daemon/selection singleton, valid nonnegative revision, Core desired state and routing mode, <=1 active apply and one active inert restore preparation. Compute and match actual SHA-256 of applied/LKG config, optional manifest and source-map BLOBs to their recorded digests. Do **not** infer other unreferenced generations, file-resource inode integrity, Core network health or encrypted archive HMAC from this subset.
4. `--mode verify` (manual **after** the guest has restarted) requires an exactly operator-pinned baseline SHA-256 and the ADR 0128 host-side `observation-<nonce>.json` with status `virtual_guest_forced_off_observed`, matching exact case/nonce/domain/UUID and all proof/restore/delete flags **false**. Re-read the *actual* guest SQLite using the same independent checks. Any difference to the original subset, `recovery_required`, active apply attempt, missing witness, stale/replaced file or invalid SQLite refuses and prints no success report. Prepared inert-restore audit journal count may remain 1 but cannot authorize import or GC.
5. A successful **subset** read explicitly reports `guest_reboot_verified=false`, `physical_power_loss_verified=false`, `core_health_verified=false`, `archive_hmac_verified=false`, `restore_authorized=false` and `metadata_deletion_authorized=false`. This tool does not prove the user-session VM was actually rebooted, physical power failed, the live Core is listening, or the full T15/T23 invariants have been verified. Another operator-controlled reboot log and independent source HMAC/CAS/resource checks are still required.
6. Never issue `virsh` commands, modify the production SQLite state, repair WAL/journal, auto-restart a Core, truncate a file, delete an orphan, import credentials or clean up a damaged fixture. The only write operation is exclusive, bounded host-witness-compatible baseline creation under the fixed disposable lab directory.
7. Normal CI must run synthetic tests with a deliberately minimal v18-shaped SQLite database and mock host stop witness. Test exact baseline match; changed selection/generation SHA, forged host stop flags/UUID, wrong baseline digest, unreconciled active apply, wrong schema, symlink/unsafe file and duplicate baseline all fail closed. These tests **do not run a VM or produce actual power-loss evidence**.

## Acceptance boundary and future work

This is a **subset checker**, not a genuine recovery test. Before T15/T23 completion, still add guest fixture instrumentation at actual fsync/SQLite/Core boundaries, independent reboot/event attestation, full schema + unreferenced domain tables, source/resource inode+SHA validation, signed encrypted archive HMAC and original-vs-detached reclaim proof, real active Core port/route observations, double rollback fault cases, genuine storage power-fault replay and an operator-approved retention policy. PR #1 remains Draft; no stable `main` changes until the explicit long-run/compatibility gates.
