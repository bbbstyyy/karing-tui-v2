# ADR 0131 — Cross-language contract: real v18 Go Store ↔ read-only guest SQLite auditor

- **Status:** M4 internal regression only. Neither T15 nor T23 is accepted; no real guest interruption or physical power loss has been performed by these tests.
- **Depends on:** ADR 0128 guarded host VM-stop tool, ADR 0129 Python guest-side read-only SQLite subset verifier and ADR 0130 real v18 prepared-journal guest fixture.
- **Preserves:** Linux ordinary user, no TUN, CN's original 28 preset groups, five-layer Custom → GeoSite → GeoIP → ACL → FINAL order, and exclusion of subscription/ISP-supplied routing.

## Discovered coverage gap

ADR 0129's Python `unittest` uses a deliberately minimal SQLite v18-shaped *synthetic* database to validate safe input handling. ADR 0130's Go fixture uses the real `storage.Store` and real v18 migrations, but until now these two have never been exercised on the **same real database**. This leaves a schema/WAL/journal interoperability risk: both independent test suites can be green even if the Python guest audit cannot read the actual Go Store, silently misses a current field, or declares an unreconciled `prepared` journal safe.

## Decision

1. Add `internal/storage/t15_guest_sqlite_crosscheck_linux_test.go` as a bounded, Linux-only cross-language integration regression. It creates **only** owner-private synthetic files under `t.TempDir()`, then uses actual Go `storage.Open` v18 and `PrepareApply → BeginActivation → BeginVerification → CommitApplied` to seed a committed initial Applied/LKG without starting or checking Core. A second variant uses the production `PrepareApply` to persist a pending **unactivated** journal.
2. After closing the Go Store, invoke the original `scripts/recovery_lab/guest_reboot_audit.py` executable from CI's available `python3`; do not copy the Python logic into Go or rewrite a fake schema for this test. Bind the auditor to the exact disposable VM-name/UUID/case/nonce acknowledgment and a fixed owner-private per-nonce lab directory under the test-only XDG state root. The Python process may only read the Go v18 DB and write its non-overwriting private baseline within the ephemeral lab.
3. Check a genuine Python `capture` report and independently validate its baseline JSON SHA from Go test code. Inject **synthetic non-authorizing host-stop JSON** with all power-loss/reboot/restore/deletion flags explicitly false. This is merely a parser test, **not a true host observation or an attested virtual stop**. Invoke Python `verify` and require `sqlite_subset_consistent_manual_review_only` for an unchanged *committed* database, with `guest_reboot_verified=false`, `core_health_verified=false`, `archive_hmac_verified=false`, `physical_power_loss_verified=false`, `restore_authorized=false`, `metadata_deletion_authorized=false`.
4. Hash/byte-compare the real Go SQLite main file before/after the read-only Python audit; no write, upgrade, schema migration, Core activation or recovery is authorized by this check. Mutate selection using Go's real `SetCurrentSelectionIntent` after the baseline, close it, and require Python verification to refuse the drift.
5. For the real Go **pending prepared journal**, both capture and SHA pinning must work, but `verify` must **refuse** even if the observed SQLite fields match the pre-cut baseline: pending active apply is a manual hold. On that synthetic test SQLite *only*, run real `RecoverInterrupted`, verify the pending journal is marked interrupted while the prior Applied/LKG remain, and require the **old** baseline to remain invalid after the recovery modification. Also require a forged VM UUID in the synthetic witness to be rejected.
6. Tests run in ordinary Go CI and its four Race shards, with a strict opt-in Python presence requirement in CI. They never call `virsh`, kill or restart a VM, inspect a real host SQLite, import credential databases, grant backup restore permissions, or publish a marker for an actual force-stop. An apparent cross-language success does **not** close any physical power-loss or after-reboot safety gate.

## Remaining acceptance gates

Actual T15/T23 requires the independently created disposable guest reaching a real checkpoint, host-side power fault (with correct storage durability model), independently witnessed restart, complete rule/resource inode and SHA chain, archive/attestation HMAC verification, real Core traffic state, idempotent journal reconciliation and failure of the rollback itself; only then consider broader tested restore transactions and an operator-approved retention/metadata deletion protocol. M4 full functionality, CN offline license, T25 72h/7d/30d soak and stable `main` merge remain open. This branch is stacked on ADR 0130 and must be rebased/revalidated against its final approved development merge before independently merging.
