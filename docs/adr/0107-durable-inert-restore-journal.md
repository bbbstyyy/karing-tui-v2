# ADR 0107 — Durable inert preparation journal with atomic live CAS (SQLite v18)

- Status: **M4 internal-only, inert durability and crash-recovery prerequisite**. NOT backup restore, SQL import, activation, or durable executable resource leasing.
- Depends on ADR 0086 and 0101–0106, and leaves T15/T23 / M4-M5 release gates OPEN.
- Linux ordinary user, no TUN; CN 28 preset groups, Custom → GeoSite → GeoIP → ACL → FINAL; no subscription/ISP routing layer.

## Decision: isolated, non-activating journal

Introduce **SQLite schema v18** with `inert_restore_preparations`, an entirely separate table from existing `apply_journal` and `apply_history`. Its two phases are **`prepared` and `abandoned` only**. A constraint binds phase to a single nullable `active_slot`; a UNIQUE constraint allows at most one pending candidate. A maximum of **32 total records** is an explicit bounded-retention refusal, not automatic deletion or rotation. Each row stores only (1) a vetted `.ktui-restore-v1-<random>` basename, never an absolute path, (2) encrypted archive and manifest SHA-256, ciphertext byte size, (3) a canonical JSON serialization of ADR 0105's **nonsecret** current-state CAS fence and its SHA-256, plus timestamps and row phase. The table holds **no backup key, plaintext SQLite, node or subscription source, restored generation, new config, executable core, or permission to activate**.

`storage.PrepareInertRestoreRecord` validates bounds, canonical fence and exact resource hashes, then enters a short SQLite transaction. The SAME transaction uses the ADR 0106 guarded no-change `UPDATE` to acquire SQLite's single-writer slot and compares the entire current applied/LKG/declaration/selection/config/core/routing fence. It then checks pending/count quotas and INSERTs the *inert* record. **Commit** is the only durable transition; any failed CAS, busy slot, canceled context or fault before commit rolls back the entire row and leaves existing applied state intact. It does not allocate a generation or use the real apply coordinator. After commit, a new writer may change the live state, which makes the old baseline stale; the row is never a restore permit.

`backupclosure.PrepareInertRestoreCandidateRecord` ties this to the locked encrypted candidate from ADR 0104. Before calling the transaction it repeats the full independent HMAC, resource, SQLite/schema and profile inspection and the read-only live fence. The ciphertext path, key and private data are not stored in SQLite. Another process may only `RevalidateInertRestoreCandidateRecord` by independently reopening the exact private candidate under `flock`, supplying the key, inspecting the durable journal from SQLite again, redoing the full candidate authentication and comparing the live fence; **successful revalidation grants no restoration rights**.

`InspectInertRestoreRecords` provides a bounded fail-closed read-only inventory. Rows marked `prepared` after restart must always report `RequiresRevalidation=true`: they are *possibly interrupted*, not “resumed,” and do not attest a surviving process lease. `AbandonInertRestoreRecord` is the sole supported state transition (prepared → abandoned), requiring exact ID, candidate basename and ciphertext digest. It is explicit and only modifies the inert journal; it NEVER unlinks, prunes, imports or activates a candidate. Actual ciphertext deletion is a separate, safely locked ADR 0104 operation. No automatic GC, timer or PID-based orphan cleanup.

## Schema evolution and archive compatibility

The v18 migration is transactional on a normal `storage.Open`: it does not rewrite existing configuration/declaration/profile tables. A pre-v18 executable cannot open a v18 file, and rolling back the *program* therefore requires restoring its prior intact DB backup, not downgrading in place. New encrypted archive snapshots encode storage schema v18. Existing v17 encrypted archives continue to pass **read-only** inventory, migration, exact schema and profile audit checks using a separately migrated **v17 in-memory reference**; v18 archives compare against v18. This preserves old ciphertext inspection without treating v17 and v18 as writable cross-version import formats.

For v18 archived SQLite, the independent schema/domain verifier validates each bounded inert journal row's canonical digest and format and **rejects any `prepared` row**. A new backup captured while an inert preparation is pending must not accidentally establish restoration authority from a stale candidate pointer. Only empty or all-abandoned inert journals are accepted by archive preflight. This is a deliberate conservative availability tradeoff, not an implicit deletion.

## Crash and fault boundaries

Tests inject a SQL error after INSERT but before commit, cancellation during the transaction, bad digests/scopes, stale selection CAS, duplicate pending records, corrupt durable journal bytes, and restart reopening. Linux forked subprocesses are **SIGKILLed before and after commit**: before commit, the journal must be absent and SQLite writer lock released; after commit the row must persist but remain untrusted/unrestorable and explicitly abandonable. Storage snapshots, active/LKG generations, the actual apply journal and core lifecycle must remain unchanged. An approved real sing-box v2 candidate is included in managed-core integration; even that fully authenticated binary cannot create an activation path.

## Deferred release gates

This is **NOT** a committed restore transaction: it commits *only* inert evidence. There is still no isolated plaintext staging/import transaction, declared migration policy, durable generation/resource leases, restore-specific state machine capable of activation, daemon operation gate integration, core Check/Activate/Verify, dual rollback, T15/T23 crash injection or large (over 64 MiB SQLite) authenticated restore. Future stages must bind actual resources to a recoverable committed apply transaction and repeat a fresh atomic CAS there; neither a previously prepared row nor a revalidation result may substitute. `RestoreSupported=false`, `RestoreReady=false` remain unconditional, no CLI/HTTP/TUI restore API or background process is added.
