# ADR 0066: Expose guarded Profile Source management over the local API

## Status

Accepted.

## Context

M3 implements subscription source persistence, immutable snapshots and a bounded refresh scheduler, but a usable Linux daemon also needs a local management path that does not require editing SQLite or a runtime sing-box JSON file.

Metadata-only HEAD requests already use an independent request-start observation clock and source revision CAS. Full refreshes own a crash-recoverable profile update lease and may produce blocking compatibility diagnostics. These workflows must remain separate from applying a runtime declaration.

## Decision

The permission-restricted local Unix socket exposes four source operations:

- `GET /v1/profiles`: list known profile sources in stable profile-ID order.
- `GET /v1/profiles/{profile_id}`: read the revisioned source configuration and full-refresh status.
- `PUT /v1/profiles/{profile_id}`: create with expected revision zero or edit using optimistic source revision CAS.
- `POST /v1/profiles/{profile_id}/refresh`: explicitly fetch and analyze the source; requires a positive expected source revision, with empty updates blocked unless `allow_empty` is explicitly set.

All input JSON is size bounded, rejects unknown fields and trailing values, and passes through the domain source validator. The duration field is checked in integer seconds before conversion to prevent overflow. Manual update identifiers are generated by the daemon, never accepted from untrusted clients.

The HEAD metadata endpoint and source modification/manual refresh endpoints share a four-operation HTTP API gate with per-profile non-reentry. Independent scheduler work retains its own bounded global budget, with the durable store lease and revision CAS preventing conflicting commits. A manual full refresh has a 60-second deadline, and the Unix socket client uses a longer dedicated timeout.

Successful manual refresh responses identify the accepted source revision, current snapshot, node count and ignored/compatibility diagnostics. A blocking import refuses the candidate and reports diagnostics. Read-only source queries do not modify snapshots.

Most importantly, manual refresh **does not** implicitly perform snapshot-to-declaration replacement, configuration compilation or core application. The current applied generation remains authoritative until a later explicit revisioned apply operation.

## Fault behavior

- stale revision, disabled source and active update lease: conflict;
- unsupported source, import fields or unconfirmed empty update: unprocessable input;
- unavailable selected fetch path: service unavailable;
- network/timeout/bounded-size failures: distinguished errors without replacing last-known-good snapshots;
- exhausted HTTP API operation budget: too many requests with a short Retry-After.

Source usage metadata and HEAD observation timestamps are separately persisted. A HEAD response started before a newer full-refresh observation cannot overwrite it after finishing later.

## Validation

Tests cover API create/get/list, source revision CAS and duration overflow, manual accepted import, blocking diagnostics that preserve the existing snapshot and running generation, HEAD/full-refresh/source-edit gate competition, and Unix socket client CRUD. Background/full-refresh overlap tests verify old HEAD results never replace newer persisted usage.

## Consequences

This is the M3 management foundation for future CLI/TUI subscription screens and explicit apply previews. It is **not** an assertion of full Clash/V2Ray/provider format compatibility, automatic apply correctness, or completed node filter execution.
