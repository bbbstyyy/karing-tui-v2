# ADR 0119 — Durable signed per-rule unlink intents and explicit crash-resumable reclamation

- Status: **M4 internal-only, per-file physical cleanup prerequisite**; no automated garbage collection, full-directory deletion, restore/import, Core execution or public CLI/TUI/API.
- Extends ADR 0114–0118. SQLite schema remains **v18**, and the ciphertext backup, existing live state, apply journal, rule-store and original Karing routing format remain unchanged.
- Ordinary-user Linux; no TUN, original CN 28 preset groups; Custom → GeoSite → GeoIP → ACL → FINAL, never add subscription/ISP routing.

## Motivation

ADR 0118 allows an authenticated retired RULES-ONLY directory to be atomically renamed into `.ktui-inert-rules-reclaim-v1-<ciphertext-sha>`. Its old staging and audit paths reject this scope. No rule bytes have been removed. A naïve `RemoveAll`, time-based GC or loop of `unlinkat` calls would not distinguish a partially deleted recovery scope after SIGKILL or a machine crash, and could delete an unrelated file substituted after validation. A successful preflight report is not a durable file lease.

ADR 0119 adds a **bounded, explicitly invoked single-leaf physical unlink protocol**, where every omission can be rechecked against authenticated, durable per-leaf authorization. The invariant is: **no absent file is trusted unless the entire original rule inventory was durably committed first and a separate authenticated, fsynced intent for that exact leaf was committed before unlink**.

## Decision

Three internal-only APIs, all on an explicitly acquired `InertRestoreResourceLease`, require the original caller-supplied 32-byte key and exact still-prepared v18 journal record.

1. `PrepareDurableRuleReclaim(ctx, key)` derives only the fixed, UID-owned, private `<live-db-parent>/inert-rule-bundles/.ktui-inert-rules-reclaim-v1-<authenticated-ciphertext-sha>` root and holds the original ciphertext directory flock/mutex followed by the same staging-root flock as ADR 0114–0118. Revalidate full encrypted ciphertext HMAC/SHA, in-memory SQLite/schema/profile and all Applied/LKG/declaration/selection/Core CAS.
2. Before any unlink, inspect **all** 1–128 canonical JSON/SRS leaves from the authenticated archive, max 128 MiB, using exact size and SHA-256 through `openat(O_NOFOLLOW)`, 0400 current-UID one-link non-executable files and 0700 UID-owned scope/root. Refuse extra/unknown entries, pending/retired/other reclaiming siblings, directory replacement and any existing plan (even malformed). Generate one deterministic, size-bounded immutable `.ktui-reclaim-plan-v1` record containing format/version, source archive/inventory digests, prepared-journal ID, reclaim directory device/inode, and sorted exact per-file basename/size/digest/device/inode. Authenticate the canonical JSON plan by HMAC-SHA256 using the caller-supplied archive key with a dedicated **domain separator**.
3. Publish the plan with parent-relative `O_CREAT|O_EXCL|O_NOFOLLOW`, require a real current-UID one-link 0400 private file, fsync it and the containing directory before returning. If power fails after create but before durability is known, a partial/malformed plan is a **blocker**; do not overwrite, delete or auto-adopt it. A successful plan allows only later explicit one-leaf calls; it performs **zero** unlink operations.
4. `InspectDurableRuleReclaim(ctx, key)` reopens the original ciphertext lease and verifies the signed plan, its exact journal ID, directory identity and complete original archive inventory. Inspect a fresh directory FD twice, accepting **only** the plan, canonical per-file intent names and the exact remaining original rule leaves. Every present rule must rehash to the original size/SHA-256, UID/0400/single-link inode from the signed plan. Every missing rule must have its own valid, private, fsynced `.ktui-reclaim-intent-v1-<three-digit-index>` file with HMAC bound to the signed plan digest, exact index and rule basename. A missing rule with no matching intent is always refused. Do not accept unknown/symlink/hardlink/executable items. Recheck full ciphertext/journal/live CAS and parent/scope identity, return only digests, counts and unlinked-byte totals, **not** an authority token.
5. `UnlinkNextDurableReclaimRule(ctx, key, expected)` is an **explicit one-leaf call**, never a loop, scheduler or user-facing cleanup command. Treat the supplied progress report only as an optimistic CAS fence: independently reopen/revalidate original ciphertext, prepared journal, entire plan/remaining-file set and live state first. Choose one originally signed, still-present leaf. If its signed intent is not yet present, create a dedicated 0400 HMAC intent with O_EXCL and fsync the intent **and containing directory**, before attempting an unlink. Re-read the whole remaining namespace, replay full journal/live CAS and independently verify the selected original file's SHA/size/inode via O_NOFOLLOW. Only then perform a single `unlinkat(dirFD, leaf, 0)`, never an arbitrary caller path. Fsync scope after unlink and recheck the authenticated remaining subset and live CAS.
6. A failure **before** the per-file intent: no deletion was attempted. A failure after intent fsync but before unlink: the signed intent exists while bytes are still present, and the next explicit call may revalidate and resume. A failure after unlink but before scope fsync: the leaf may be absent even though the caller receives an empty/failed result; a fresh lease uses the already durable signed intent to authenticate this missing leaf and continue. No automatic retry, rollback of a partial deletion, blind cleanup or promise of power-loss durability is made. An unexpected missing rule **without** a signed per-file intent is never accepted.
7. A successful `DurableRuleUnlinkResult` confirms only one exact inactive rule was unlinked; `DurableRuleReclaimProgress.UnlinkedBytes` is a sum of authenticated absent-file lengths, **not a guarantee that disk blocks were freed** (e.g., another process may hold the inode FD). The immutable plan and per-leaf intents remain private inside the reclaim directory even when all rule bytes are gone. No final directory removal exists, and no active Core/SQLite/ruleset or running daemon state is changed. Both restore flags are always false; reports expire when returned.

## Crash, concurrency, and threat boundary

- Lock order is **candidate lease mutex / held ciphertext flock → dedicated stage-root flock → reclaim scope FD**; no caller-supplied paths or relative rule names can escape the canonical inventory. `Close` is serialized by the lease mutex.
- No automatic deleting of files merely because an old receipt, old inode number, age or directory name matches. Exact HMAC intent files are a prerequisite for tolerating missing leaf data after a crash. The original content SHA-256 and size must still match for every remaining original file.
- The HMAC uses the existing per-archive key but a dedicated domain; its integrity is checked in constant time, and no key/ciphertext plaintext or absolute path appears in reports. Any unexpected added, replaced or malformed entry blocks the entire operation.
- The exclusive root flock protects **cooperating** writers. A deliberately malicious same-UID/root process not respecting flock can race path syscalls; no filesystem user-space code can promise stronger isolation under that threat. The project explicitly requires a private Linux state directory and refuses observed changes.
- fsync and the injected SIGKILL boundary exercise interruption behavior, but **real power-loss durability is not proven** without T15/T23 fault-injection machinery. A crash might leave a partial marker, for which the only automatic behavior is refusal.
- The plan permits each leaf to be removed only by a separate explicit invocation. This operation does not alter journal phase, delete the ciphertext candidate, clean unknown orphan scopes, or remove the emptied reclaim directory. Final cleanup, quota reclamation policy and full restore transaction remain separate reviewed work.

## Verification

- Signed complete plan creation/reinspection with zero implicit deletion; existing plan cannot be replaced. Explicit one-leaf unlink produces an individual signed/fsynced intent before missing data is accepted; a second call with stale report is refused.
- Tampered plan, wrong key/expected SHA, missing file without intent, symlink, public mode, executable file, unknown entries, in-call same-byte inode swap, selection/journal CAS drift and cancellation all fail closed.
- Deterministic fault hooks before/after unlink preserve no false success receipt; a correctly signed intent permits cross-call reauthentication of both still-present and already-missing data. Linux child process SIGKILL after one `unlinkat` is followed by independent ciphertext-lease reacquisition and inspection, without mutating Applied/LKG.
- Managed, repository-approved real Core integration verifies the same durable plan and one explicit rule unlink while retaining the live Core and original running configuration untouched.
- Existing CI's full `go test -race` covers the unusually expensive encrypted/SQLite recovery matrix with an explicit **30-minute** Go test timeout; this is a time budget adjustment, not test omission.

## Remaining release blockers

Physical cleanup only occurs one authenticated leaf at a time. **Not implemented:** final plan/marker removal, automated garbage collection, orphan pending directory resolution, cross-filesystem quotas, real power-loss replays, complete backup restoration, credential-bearing SQLite migration, active resource publishing and validation, Core Check/Activate/Verify, multi-layer rollback/rollback-of-rollback, T15/T23 acceptance and 72-hour/7-day/30-day long-duration stability and CN offline-resource licensing evidence.

PR #1 stays **Draft** and `RestoreSupported=false`, `RestoreReady=false`; there are still no user-facing backup, restore, or cleanup operations.
