# ADR 0118 — Cross-restart retired-rule attestation and non-deleting reclamation intent

- **Status:** M4 internal prerequisites only; no rule unlinking, database import, Core execution, public backup/restore/cleanup entrypoint or restore authorization.
- Extends ADR 0114–0117; SQLite schema remains **v18**, without any changes to backup ciphertext, live rules, generations, apply journal, subscription records or compiled native config.
- Linux ordinary UID, no TUN, preserve CN original 28 presets and Custom → GeoSite → GeoIP → ACL → FINAL; no subscription/ISP routing layer.

## Problem and explicit safety split

ADR 0117 only renames an independently authenticated, *inactive* rules-only scope from `.ktui-inert-rules-v1-<archive-sha>` to `.ktui-inert-rules-retired-v1-<archive-sha>`. The original reader and publisher deliberately reject retired names, so no safe post-restart inspection was available. Returning a namespace receipt at retirement time is not sufficient: all process-local FDs and flock leases disappear at SIGKILL, and the same UID can replace files after a prior successful report.

Physical deletion is irreversible one leaf at a time: a SIGKILL between two `unlinkat` operations can leave a subset whose missing data cannot be reauthenticated using ADR 0116's *complete* file-list comparison. Deleting now without a durable subset inventory/restart procedure would violate the project's crash-safe operating objective. Therefore split the reclaim work into **read-only cross-restart attestation and a durable namespace intent** (this ADR), followed by a **separate future durable unlink/resume transaction**. ADR 0118 **does not free disk space**.

## Decision

Add two internal Linux APIs on an explicitly reacquired `InertRestoreResourceLease`:

1. `InspectRetiredDormantRuleBundle(ctx, key) (RetiredRuleInspection, error)` is read-only. Require the exact, still-pending v18 journal record, nonzero caller-supplied original 32-byte key and a newly held ciphertext directory `flock` after process restart. Reauthenticate complete ciphertext HMAC/SHA, archived SQLite/schema/profile and full live Applied/LKG/declaration/selection/Core CAS before and after inspection.
2. Resolve **only** the dedicated, already existing private `<live-db-parent>/inert-rule-bundles` staging directory, with UID-owned 0700 and an exclusive, cooperating-writer `flock`. Reject arbitrary caller path selection and overlap with the candidate ciphertext namespace.
3. Use a separate scanner from ADR 0115 so existing normal-staging and normal-audit APIs **still reject** retired/reclaiming names. The ADR 0118 scanner recognizes at most eight complete `.ktui-inert-rules-v1-<64-lowerhex>` or `.ktui-inert-rules-retired-v1-<64-lowerhex>` scopes; unknown/pending/reclaiming entries, symlinks, extra files, invalid paths and relaxed permissions cause a whole-operation refusal. All complete scopes must have 0700 owned real directories and 0400 UID-owned one-link non-executable canonical leaf files.
4. Select **only** `.ktui-inert-rules-retired-v1-<authenticated-ciphertext-sha>`, require the **exact set** of 1–128 SHA-named JSON/SRS files from the authenticated encrypted inventory (maximum 128 MiB in total), verify size, independent SHA-256, private permissions and per-file inode identity via `openat(O_NOFOLLOW)`. Reopen fresh directory descriptors, repeat the entire namespace and byte checks, revalidate the original encrypted candidate/journal/live CAS, and recheck root and source inode identity. A successful report returns only ciphertext/inventory/scope-name digests, file count/bytes and `ContentVerified=true`; `RequiresRevalidation=true`, `RestoreSupported=false` and `RestoreReady=false`.
5. `BeginRetiredDormantRuleReclaim(ctx, key, expected)` requires explicit caller intent and a previously obtained **non-authorizing expected report**. While holding ciphertext lease and private-stage parent `flock`, independently authenticate all the same file bytes, inventory, CAS and inode identities again, before issuing **exactly one** `renameat2(RENAME_NOREPLACE)` from the fully verified retired name to `.ktui-inert-rules-reclaim-v1-<authenticated-ciphertext-sha>`. Refuse collisions; do not silently accept an already reclaiming scope. Validate the exact name transition and unchanged file bytes/identity, fsync both directory and parent and repeat live CAS.
6. A failure **before rename** means zero mutations. A failure or SIGKILL **after rename** means uncertain durability: return an **empty result**, retain files, and do not automatically roll back/overwrite/adopt or proceed to deletion. The original ADR 0114/0115 and the new ordinary retired reader **all reject reclaiming names**. A future physical-reclamation procedure must explicitly authenticate its durable intent, validate allowed remaining-file subsets and authorize every unlink with fresh inode/CAS evidence; it must not treat this receipt as an unlink permission.
7. A completed `RetiredRuleReclaimIntent` returns only archive/inventory/reclaim scope digests, rule count/bytes, `IntentPublished=true`, `BytesDeleted=false`, `RequiresManualReview=true`, and both restore flags false. No absolute names, ciphertext key, plaintext rule, SQLite credential record, executable Core, source FD or valid restore handle leaves the operation. This is an **irreversible namespace intent only** and not physical garbage collection.

## Concurrency and crash guarantees

- Lock order: ciphertext resource lease mutex/held candidate-directory flock → exclusive private-stage root flock. No existing lock order is reversed, and parent `Close` cannot race an in-process inspection or rename. This does **not** protect against deliberately malicious actors sharing the same UID outside the cooperative protocol.
- Validation occurs on *real no-follow FDs*, not paths obtained from the caller. Same-byte inode replacement **during one held-lock validation** is detected by pinned identities and repeat scans. A replacement **between independent calls** cannot be compared against the closed prior inode and is independently reauthenticated from its exact size/hash/UID/mode on the new call; a previous report is never a durable inode lease.
- An expected parent-directory mtime change from the authorized rename is allowed, but the inode, UID and 0700 privacy and path identity must remain stable. Other unexpected changes fail.
- Parent fsync only follows successful no-replace rename and reverified full bytes. An error after rename, including lost fsync, is **never** repaired automatically.
- Recovery from a partial physical deletion is expressly **not implemented here**. Never use `RemoveAll`, broad globs or time/PID GC to attempt to recover space.

## Tests and unresolved gates

- Unit regressions: post-close/reopened candidate and retired scope authenticated in a new lease, explicit transition, no active Core files affected, no deleted rule bytes, unchanged live Applied/LKG/journal and non-readoption by older APIs.
- Negative matrix: wrong key/forged SHA/count/byte/ready report, closed lease/cancellation, symlink/hardlink/same-byte inode substitution, tampered hash, permissive root/scope, extra unknown or pending namespace, stale journal/selection CAS and late root replacement.
- Post-rename failure simulation returns no success receipt and leaves bytes for manual review. A separate Linux child process reacquires the encrypted candidate, authenticates the retired rules, performs the atomic rename and is SIGKILLed before parent fsync; the parent verifies retained rule bytes and non-activation.
- Managed approved-Core integration authenticates the exact retired rules and publishes only a non-deleting reclaim-intent basename after closing original anonymous Core pins, without executing or persisting the historical Core.
- **Still open:** authenticated resumable per-file physical deletion and durable checksum-bound cleanup journal, recovery of half-deleted scope after SIGKILL/power failure, safe orphan pending-scope handling, real SQLite/credential migration, active rule installation, same-transaction restore CAS, Core Check/Activate/Verify, two-level rollback, T15/T23 power-loss tests, licensing for offline CN rules, and 72-hour/7-day/30-day soak evidence. PR #1 remains Draft; no user-facing restore or cleanup route is enabled.
