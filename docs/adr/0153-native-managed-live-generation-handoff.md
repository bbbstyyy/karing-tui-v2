# ADR 0153 — T24 native managed live-generation handoff on a valid declaration CAS

- **Status:** synthetic T24 preflight only; no general online upgrade, production release, restore/GC, offline distribution or long-soak approval.
- **Depends on:** ADR 0149 managed applied Core startup, ADR 0150 three-entry isolation, ADR 0151 Selected-node fail-closed recovery, and ADR 0152 durable unapplied declaration / stale apply CAS refusal.
- **Unchanged scope:** ordinary-user Linux amd64 and arm64, no TUN, no network takeover, no subscription/ISP routing layer, 28 CN preset groups and Custom → GeoSite → GeoIP → ACL → FINAL untouched; no CN SRS/remote DNS/provider credentials.

## Previously untested gap

ADR 0152 established that the V1 declaration head can advance independently of an Applied generation and that a stale `expected_config_revision=0` request is rejected before it changes a live Core. Its experiment explicitly **never applied** the newer revision. The real Daemon-managed activation path while **Core desired state is running** had therefore not been exercised end to end within the two native `--network none` environments. Production Go integration coverage did not by itself demonstrate that a pinned, built management CLI, private SQLite, production Unix API, approved Core process, local data plane and restart all agree on a successful live generation switch inside the offline sandbox.

## Decision

Extend the **existing fourth** independent native network-none test, retaining the first three independent containers and all pinned artifact/permission checks.

1. Keep ADR 0152's initial state unchanged: a real approved managed Core applies synthetic declaration/config revision 1, starts and passes Rule/Direct/Selected routing and bounded Selected SOCKS5 denial/recovery. A new declaration revision 2 changing **only log level warn→error** is committed and compiled, while a stale CAS apply returns 409. After an explicit stop and real Daemon restart on the same private SQLite, declaration revision 2 remains unapplied and config revision 1 still runs the original local routes.
2. During **that second Daemon session**, immediately after verifying old-generation traffic and failure isolation, re-read the immutable declaration head SHA/revision 2, compile it again, require the exact previously observed deterministic native config SHA, no SRS and unchanged private-local-only routing. A valid `POST /v1/declaration/apply` uses `declaration_revision=2` and **`expected_config_revision=1`**. An explicit operator-style apply is intentionally **disruptive**, not a claim of uninterrupted existing connections.
3. Require HTTP 200 with an actual positive persisted attempt ID and strictly newer generation ID, original base config revision 1, new target config revision 2, and declaration/config SHA equality with the two immutable preview identities. Validate live Daemon status reports **config=2, declaration=2, Applied=LKG=new generation**, `desired=running`, `state=running`, no recovery, no active operation or open circuit. Require a **different PID** from the pre-apply process and independently verify that this running PID is a same-UID direct child executing the exact pinned Core binary.
4. Exercise all three *real* managed inbound TCP SOCKS5 local echo paths after the switch. Rule/Direct must not cross Selected; Selected must use exactly one synthetic local node. Also inject an application-level Selected SOCKS5 CONNECT refusal, require Rule/Direct remain usable, and clear refusal for a new successful Selected relay **without another Core PID change**.
5. Explicitly stop, confirm stopped desired state, no PID and no default listeners, then launch a **third** Daemon session on that *same throwaway SQLite*. Prove the new generation/LKG/revision 2 and declaration SHA survive restart without automatic Core start. Explicitly start the newly applied Core and repeat real three-inbound forwarding, selected refusal/recovery, same-UID executable identity, final durable stop and port cleanup.
6. Standard CI adds fast Python regressions to reject malformed/lying successful-apply receipts, unchanged generation, missing promotion to LKG, mismatched/config/declaration revisions, PID not changing on live promotion, recovery state, active apply state and lost data-plane verification. The exact latest-head native amd64 **and** arm64 Core Provenance, full Go/Python tests, four Race shards and Managed Core must pass before this draft PR can merge.

## Boundary

The second candidate is **a local-only synthetic log-level change**; there are no real CN rule sets, DNS lookups, remote nodes, credentials or external traffic in the container. Successful apply proves controlled generation replacement and post-switch local data-plane health; it does **not** prove zero-downtime connection preservation, complicated five-layer interleaving, remote-failure recovery, two rollbacks, real host reboot/power loss, portable offline tar, license closure, or T25 72h/7d/30d soak. T15/T23/T24/T25 and M5 release/restore/GC gates remain **OPEN**; `core_distribution=false`, `cn_preset_offline_bundle=false`, stable `main` untouched and outer release PR #1 remains Draft.
