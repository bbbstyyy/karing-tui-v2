# ADR 0104 — Persistent inert encrypted restore candidates with re-adopted process leases

- Status: **M4 internal-only candidate staging / recovery precondition**. No backup import, SQL restore, activation, API, or TUI.
- Based on ADR 0094–0103; `docs/plan.md` M4, T15/T23 remain open.
- Linux unprivileged, no TUN, CN 28 built-in groups and Custom → GeoSite → GeoIP → ACL → FINAL unchanged; subscription/ISP are not routing layers.

## Decision

`StageInertRestoreCandidate(ctx, sourceArchive, candidateParent, key)` first runs the existing bounded full HMAC, per-record SHA-256, independent SQLite integrity/schema/profile-domain preflight (ADR 0101–0103). It then takes an exclusive `flock` on an EXISTING caller-supplied UID-owned 0700 **dedicated candidate parent**. A bounded scan (maximum **8** scopes) refuses unknown entries, symlinks, unsafe ownership/modes and retention overflow. Under the parent lock it creates a new 0700 `.ktui-restore-v1-<random>` directory and acquires a separate exclusive `flock` on that directory. A single 0600 `candidate.ktbackup` is exclusively created with `O_NOFOLLOW`, filled by copying only authenticated ciphertext, compared byte-for-byte by a streaming SHA-256 and exact length, fsynced and bound to the inode before source/target folder fsync. The writer verifies the copied archive's HMAC, all records, independent SQLite schema/profile checks AGAIN before returning an inert candidate handle. No plaintext database, node, rule or core appears in the candidate scope.

The directory lock is a **live-process exclusivity lease**, NOT a durable lease spanning process death. `Close` releases the file descriptor but *leaves the encrypted scope intact*. A crash also releases its Linux flock. `ReopenInertRestoreCandidate(ctx, path, key)` first coordinates with the dedicated parent lock, obtains the exclusive child lock, checks exact filename/inode/UID/modes, and **independently re-authenticates the full ciphertext and SQLite logical/state integrity with the caller-resupplied key**. Thus only encrypted bytes and the directory name persist across restarts; no ephemeral preflight report or lease is trusted across process death, and the symmetric key is NEVER written to the scope.

`Verify` retains its current-process exclusive directory lock while rechecking complete ciphertext and preflight evidence. A second opener sees `ErrInertRestoreCandidateBusy`, and no other process may treat that scope as its candidate until the lock is released. `Discard` is an explicit, internal-only, nonrecursive cleanup on that *held* scope; it refuses unknown sibling files, symlinks, foreign/multi-linked data, unsafe ownership, ambiguous directory identity, and deletes only the single known ciphertext file with `unlinkat`, followed by directory/parent fsync. A failed/partial or tampered candidate is NEVER automatically pruned. Neither elapsed age nor a PID file provides deletion authority.

## Retention, trust and remaining recovery work

Stage refuses an archive not fully preflight-verified, a wrong/zero key, an unsafe parent or a full/unknown candidate directory. A separate disk-space check leaves a 64 MiB free-space reserve but does not actually allocate/reserve blocks against unrelated processes. The existing in-memory SQLite preflight remains capped at 64 MiB even though encrypted archives may be larger. The model assumes other same-UID processes are trusted: an adversarial same-UID pathname/rename race is not solved by advisory flock. fsync failure after scope creation may leave an **uncertain encrypted orphan** for human review, never an automatic retry/import.

Tests cover ciphertext equality and privacy, unchanged live daemon state, Close/reopen, wrong key and altered ciphertext refusal, duplicate-process lock rejection, child SIGKILL and fresh key-based re-adoption, unknown extra files and full retention refusal, plus a genuine pinned-core v2 candidate lifecycle in managed-core integration.

There is **no persistent lock held while the process is dead**; an actual future restore transaction must acquire NEW simultaneous durable resource generations/leases, verify the candidate and all referenced resources again immediately before any write/activation, and implement isolated SQL staging, migration policy, CAS apply, rollback-of-rollback and T15/T23 crash injection. `RestoreReady=false` and `RestoreSupported=false` remain unconditional. No daemon, CLI, HTTP, TUI, key manager, automatic candidate enumerator, scheduler or garbage collector is added.
